## 1. 이 문서가 **하지 않는** 것

- **"포화는 무시해도 된다" / "무시하면 안 된다"를 판정하지 않는다.** 재는 것까지가 몫이다.
- **`TRADES_COUNT` 도 폴 주기도 바꾸지 않았다.** §5 는 비용표이지 변경이 아니다.
- **배포하지 않았다.** 스키마 v3 마이그레이션이 있으므로 재시작이 곧 적용이다 —
  시점은 코디네이터가 잡는다.

## 2. ★ 먼저: **API 는 원본 총 건수를 주지 않는다**

`docs/42` §5-5 가 요구한 첫 확인이다. 결론부터: **안 준다. 그래서 못 잰다.**

`/api/v1/trades` 응답 몸통은 배열 하나뿐이다 (라이브 캡처 `tests/fixtures/live/live_trades_us.json`,
2026-07-30 AAPL):

```json
{"result": [{"price": "331.81", "volume": "126",
             "timestamp": "2026-07-30T23:43:05.000+09:00", "currency": "USD"}, ...]}
```

- `total`·`count`·`hasMore` 같은 필드가 **없다.**
- 페이지 커서도 **없다.** `/candles` 는 `result.candles` + `result.nextBefore` 로 과거를
  이어 받을 수 있지만(`api/client.get_candles`), `/trades` 에는 대응물이 없다.
  즉 **잘린 뒤쪽을 다시 요청할 방법 자체가 없다.**
- 요청 파라미터도 `symbol`·`count` 둘뿐이고 `count` 는 서버가 50으로 클램프한다
  (`api/client.TRADES_MAX`).

### 그래서 우리가 말할 수 있는 것과 없는 것

| 물음 | 답할 수 있나 |
|---|---|
| 이번 응답이 잘렸을 **가능성**이 있나 | **예** — `n == 50` 이면 그렇다 |
| 이번 응답이 실제로 잘렸나 | **아니오** — 정확히 50건이 일어났을 수도 있다 |
| 몇 건이 잘렸나 | **아니오. 영영 못 잰다** (API 가 원본 건수를 안 준다) |
| 어느 **구간**이 비었나 | **예** — 직전 응답의 최대 ts 와 이번 응답의 최소 ts 사이 |

`trades_polls_at_cap` 카운터는 **첫 줄의 뜻만** 가진다. 그 이상으로 읽으면 안 되고,
코드 주석·텔레메트리 주석·이 표가 그 경계를 세 곳에 박아 두었다.

> **만약 토스가 나중에 원본 건수를 주기 시작하면**: `/candles` 처럼 `result` 를 객체로
> 감싸는 방식이라면 `api/client._as_list` 가 `SchemaMismatch` 를 던지고
> `schema_mismatch` 카운터가 올라 조용히 지나가지 않는다. 다만 항목 안에 필드를 하나
> 더 얹는 방식이라면 **아무 신호도 안 난다** — 그건 우리가 못 잡는다.

## 3. 무엇을 만들었는가

### 3-1. 원본 건수 카운터 — 그리고 **접힘을 둘로 갈랐다** (`docs/42` §5-5)

`docs/42` 는 "응답 원본 `n` 과 저장 `stored` 를 따로 세라"고 했다. 그대로 하면 숫자가
하나 나오는데, **그 숫자 안에 성질이 정반대인 두 가지가 섞여 있어서 읽을 수가 없다.**

| 카운터 | 무엇 | 손실인가 |
|---|---|---|
| `trades_raw_rows` | 응답 원본 행 합계 | — |
| `trades_dup_same_poll` | **한 응답 안**에서 PK `(symbol, ts_ms, price_u, qty_u)` 가 못 가른 행 | **그렇다. 정보가 없어진다** |
| `trades_dup_prev_poll` | 이전 폴이 이미 저장한 행 | 아니다. 정상 **재전달** |
| `trades_rows` | 실제로 새로 저장된 행 (기존 카운터, 텔레메트리에 처음 노출) | — |

항등식: `trades_raw_rows = trades_dup_same_poll + trades_dup_prev_poll + trades_rows`.

**왜 갈라야 하는가**: 4초 폴이 수 분치를 받아 오므로 재전달은 구조적으로 크다. `n - stored`
하나만 보면 진짜 소실(같은 초·같은 가격·같은 수량인 **서로 다른 체결**이 하나로 접히는 것)이
그 안에 통째로 묻힌다. ts 가 초 단위라(`docs/41` §1, 관측 창 전 구간에서 `ts_ms % 1000` 의
고유값이 **1개**) 이 접힘은 드문 일이 아니다. `trades_dup_same_poll` 은 **그 접힘의 크기를
처음으로 재는 값**이고, `docs/42` §2 (다)의 "체결 건수의 참값"이 걸려 있던 곳이다.

두 카운터 모두 **폴 분모**와 같이 본다: `trades_polls`(빈 응답 포함) / `trades_polls_at_cap`.

### 3-2. 포화 칸을 **데이터에** — 새 테이블 `tape_gaps` (`docs/42` §5-6)

`tape_gaps` **카운터**는 "몇 번"만 알려주고 어디인지 모른다. `docs/31` 에서 W5 가 같은 문제를
로그 파싱으로 풀었다. 이번에는 한 단계 더 가서 **DB 행**으로 남긴다 (스키마 **v3**).

```sql
CREATE TABLE tape_gaps (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol       TEXT    NOT NULL,
    poll_ms      INTEGER NOT NULL,   -- 이 폴의 벽시계 시각
    prev_poll_ms INTEGER,            -- 같은 심볼 직전 폴의 벽시계 시각 (NULL = 재기동 직후)
    gap_lo_ms    INTEGER NOT NULL,   -- 직전까지 가진 마지막 체결 ts (배타)
    gap_hi_ms    INTEGER NOT NULL,   -- 이번 응답의 최소 체결 ts (배타)
    span_hi_ms   INTEGER NOT NULL,   -- 이번 응답의 최대 체결 ts
    n_raw        INTEGER NOT NULL,   -- 응답 원본 건수. 50 이면 상한이 물렸다
    n_stored     INTEGER NOT NULL    -- 이 응답에서 새로 저장된 행
);
```

**한 행의 뜻**: *"심볼 S 의 체결 중 열린 구간 `(gap_lo_ms, gap_hi_ms)` 안의 것을 우리는
갖고 있지 않다."* `n_raw >= 50` 이면 원인이 상한이다.

#### 왜 로그가 아니라 테이블인가 — **로그가 데이터보다 먼저 죽는다**

| | 보존 |
|---|---|
| `collector.log` | `RotatingFileHandler` 32 MB × 4 (`collector/notifier.py`) 위에 `ops/rotate_logs.py` 가 20 MB 마다 압축 회전하고 **14일** 지난 압축본을 지운다 (`ops_config.yaml: log_retention_days: 14`) |
| `trades_snap` | **아무도 안 지운다.** `store/retention.py` 의 기본 대상은 `candles_1m` 뿐이다 |

즉 **체결은 영구히 남는데 그 체결의 결손 표시는 14일 뒤 사라진다.** 3주 전 구간을 분석하는
사람은 "이 구간이 포화였는지"를 물을 방법이 없다. 컬럼 추가(`trades_snap` 에)도 안 되는데,
그 테이블은 `WITHOUT ROWID` 이고 PK 가 네 컬럼 전부라 **없는 행**에는 표시를 붙일 수 없다 —
결손은 정의상 없는 행이다. 그래서 **별도 테이블**이다.

#### `prev_poll_ms` — `docs/41` 이 임계로 갈라야 했던 것을 사실로 가른다

`docs/41` §4-2 는 결손 2,580줄 중 793줄을 **"prev_max 가 1시간 넘게 오래되면 tier3 재진입"**
이라는 임계로 걸러야 했다. 로그에 폴 시각이 없어서다. `prev_poll_ms` 는 그 추측을 없앤다:
`poll_ms - prev_poll_ms` 가 폴 주기 수준이면 폴링이 연속이었던 것이고, 크면 그 심볼이
그 사이 tier3 에 없었던 것이다. **NULL 은 "재기동 직후라 보증할 수 없다"** 이고,
상태 파일에 직전 폴 시각을 **일부러 저장하지 않는다** — 저장하면 정지 구간을 가로질러
"연속이었다"고 말하게 된다.

#### 디스크 비용

| 계열 | B/행 (인덱스 포함, 실측) | 행/일 | MB/일 |
|---|---:|---:|---:|
| `rankings_snap` | 192.1 | 1,428,899 (최근 24h) | **274** |
| `trades_snap` | 49.7 | 79,492 | **4.0** |
| **`tape_gaps` (신규)** | **91.1** | **~615** | **0.056** |

`tape_gaps` 는 **하루 56 KB, 1년 20 MB** 다. 랭킹 하루치의 **0.02%**.
(랭킹은 08-07 22:26 에 타입이 2→3 으로 늘어 아직 완전한 하루가 없다. 코디네이터 계획치
425 MB/일 을 쓰든 실측 274 MB/일 을 쓰든 위 결론은 안 바뀐다.)
회전·아카이브 대상에 넣지 않았다 — 이 크기에서 지우는 것이 손해다.

## 4. ★ 하류가 읽는 법 — **안 적으면 아무도 안 쓴다**

### 4-1. 원칙

**포화 구간을 빼는 것이 아니라, "여기는 테이프가 끊겼다"를 알고 계산하는 것이다.**
`docs/42` §4 가 경고한 대로 결손은 무작위가 아니라 **사건과 상관**돼 있다 — 슈팅이
일어나는 바로 그 순간에 끊긴다. 그러므로:

- **탐지 후 남은 상승폭**처럼 사건 이후를 재는 지표는 포화 구간에서 **낙관 편향**된다.
  상승의 격렬한 부분이 통째로 빠진 채 계산되기 때문이다.
- 포화 구간을 **버리면** 표본이 사건 쪽으로 편향된 채 줄어든다. **표시하고 따로 세라.**

### 4-2. 어떤 창이 오염됐는지 판정

```sql
-- 창 [w_lo, w_hi) 안에 결손이 있었나 (연속 폴링 중 + 상한이 원인인 것만)
SELECT symbol, gap_lo_ms, gap_hi_ms, (gap_hi_ms - gap_lo_ms) / 1000.0 AS hole_s
FROM tape_gaps
WHERE symbol = :sym
  AND gap_hi_ms > :w_lo AND gap_lo_ms < :w_hi
  AND n_raw >= 50                                   -- 원인이 50건 상한
  AND prev_poll_ms IS NOT NULL                      -- 재기동 직후가 아니다
  AND poll_ms - prev_poll_ms <= 8000;               -- 폴링이 연속이었다 (§4-4)
```

한 행이라도 나오면 그 (심볼, 창) 은 **오염 표본**이다. 분석은 셋 중 하나를 골라야 한다:
① 오염/비오염을 **갈라서 두 벌** 낸다, ② 오염 표본을 빼되 **뺀 수를 리포트에 찍는다**,
③ 결손 길이를 공변량으로 넣는다. **뭉쳐서 하나로 내지 마라.**

### 4-3. 잃은 양의 하한

```sql
-- 구멍 직후 국소 체결률로 환산 (span 은 그 응답이 덮은 시간폭)
SELECT symbol,
       (gap_hi_ms - gap_lo_ms) / 1000.0 AS hole_s,
       n_raw * 1000.0 / NULLIF(span_hi_ms - gap_hi_ms, 0) AS rate_per_s
FROM tape_gaps WHERE n_raw >= 50;
```
`hole_s * rate_per_s` 가 그 구멍에서 잃은 체결의 **하한**이다. 하한인 이유: 그 국소
체결률 자체가 상한에 물린 응답에서 나온 검열된 값이다.

### 4-4. 임계 8초는 어디서 왔나 (**이 문서가 쓴 유일한 임계다**)

4초 폴이 연속이면 구멍이 폴 주기의 두 배를 넘을 수 없다. 실측이 그 모양이다 —
상한 결손 1,241건(1시간 이내) 중 **87.5% 가 4초 이하, 90.2% 가 8초 이하**다.
8~60초 구간에는 21건(1.7%)밖에 없고, 그 위는 길이가 수백~수천 초로 **자릿수가 다르다**.
그건 폴링 간격이 아니라 tier3 재진입·재기동이다.
`tools/tape_saturation_probe.CONTINUOUS_GAP_MAX_S` 에 이 값과 근거가 같이 있고,
리포트는 이 임계와 **그 효과(몇 건이 갈렸는지)를 항상 같이 찍는다**.

### 4-5. 카운터와 테이블의 관계

`tape_gaps` **카운터**는 재시작해도 안 리셋되고 07-31 부터 누적이다.
`tape_gaps` **테이블**은 v3 배포 시점부터 쌓인다. **두 값은 다르고, 달라야 맞다.**
같은 창 안에서는 `COUNT(*) = Δcounter - tape_gap_write_failures` 여야 한다.

## 5. 폴 주기를 줄이면 포화가 주는가 — **재기만 했다**

### 5-1. 방법과 그 한계

저장된 체결의 실제 ts 로 폭 P 의 고정 칸을 만들고, `(종목, 칸)` 행수가 50 이상인 칸을 셌다.
"한 응답이 덮는 시간폭 ≈ 폴 주기" 라는 근사 위에 선다.

**이 추정이 틀리는 방향** (전부 같은 쪽 — 실제 포화는 표보다 **나쁘다**):
1. **저장 행은 이미 검열됐다.** 상한에 잘린 체결이 없으므로 칸 행수가 실제보다 작다.
2. **칸은 에포크 정렬이고 실제 폴은 아니다.**
3. **접힘으로 사라진 행이 빠져 있다** (§3-1). 그 크기는 v3 배포 뒤에야 알 수 있다.

### 5-2. 표 (관측 창 3.07일, 458,544 행, 651 종목)

| 폴 주기 P | 포화 칸 비율 | **포화 칸이 가진 테이프 몫** | 칸당 행수 p99 | MARKET_DATA 계획 부하 | 목표 8.5 대비 | 한도 10 대비 |
|---:|---:|---:|---:|---:|---:|---:|
| 8s | 3.76% | 46.9% | 120 | 4.43 req/s | 52% | 44% |
| 6s | 3.14% | 39.3% | 98 | 4.84 req/s | 57% | 48% |
| **4s (현행)** | **2.15%** | **27.4%** | **71** | **5.68 req/s** | **67%** | **57%** |
| 3s | 1.47% | 18.6% | 57 | 6.51 req/s | 77% | 65% |
| 2s | 0.39% | 5.2% | 42 | 8.18 req/s | **96%** | 82% |
| 1s | 0.02% | 0.3% | 25 | 13.18 req/s | **155%** | **132%** |

계획 부하 = 고정 3.178 req/s (tier1 스윕 1500/200/45s = 0.178, tier3 호가 10/4s = 2.5,
tier2 호가 300/600s = 0.5) + tier3 체결 `10/P`. 현행 설정 실측치는 `tier3_max=10`,
`tier3_orderbook_s=4`, `usage_ratio=0.85`, `limits.MARKET_DATA=10`.

**읽는 법**: 칸 수 비율(2.15%)이 아니라 **테이프 몫(27.4%)** 이 이 표의 핵심이다.
포화 칸은 드물지만 **거기에 체결의 4분의 1이 들어 있다.** 4s → 2s 는 그 몫을
27.4% → 5.2% 로 줄인다(**5.3배**). 1s 는 예산상 불가능하다.

### 5-3. 이미 절반은 하고 있다 — 다만 **사후에만**

`tier3_trades_intervals` 가 포화 종목을 **이미 2초 주기로** 옮긴다(예산 중립: 한산한
종목에서 되돌려 받는다). 그래서 위 표의 "2s" 행이 주는 이득 중 일부는 이미 실현돼 있다.
다만 그 장치에는 세 가지 한계가 있고, 이것이 균일 2초와 다른 점이다:

- **반응형이다.** 구멍이 한 번 **난 뒤에야** 빨라진다. 첫 포화는 언제나 놓친다.
- 동시에 **최대 4종목** (`TAPE_FAST_LANE_MAX`).
- TTL **2분** 뒤 원래 주기로 돌아간다.

균일 2초는 예방적이지만 예산을 **실제로 더 쓴다**. 재배분은 공짜였고 이건 아니다.

## 6. 예산 — **평균은 여유가 있고 첨두는 없다**

`docs/37` 이 밝힌 문제 위에 이 결정이 얹힌다. 같은 로그에서 다시 쟀다
(08-04 22:33 이후 텔레메트리 창 802개, 창당 5분):

| | 값 |
|---|---:|
| MARKET_DATA 평균 | **3.28 req/s** (목표 8.50, 한도 10) |
| 1초 첨두 ≥ 9 인 창 | 56.9% |
| **1초 첨두 ≥ 10 (= 한도)** | **42.9%** |
| **1초 첨두 ≥ 11 (= 한도 초과)** | **20.4%** |
| `over_limit_1s` | 10 → **34** (3일간 +24, 계속 오름) |
| `http_429_under_own_limit` | **253** |

세션별로 갈라 보면 문제가 어디 있는지 분명하다:

| 세션 | 평균 req/s | 첨두 ≥ 10 인 창 |
|---|---:|---:|
| **regular** | 4.45 | **85.4%** |
| pre | 3.89 | 62.9% |
| after | 2.55 | 7.2% |
| day | 2.06 | 3.2% |

### 그 위에서 폴을 늘리면 무슨 일이 나는가 — 정직하게

1. **429 폭풍은 아니다.** 리미터에 슬라이딩 하드캡이 있어(계약 C-4) 한도 초과가 구조적으로
   막혀 있다. **대신 호출이 대기한다.**
2. **그래서 "2초"를 지정해도 2초를 못 받는다.** 대기가 걸리는 곳은 정확히 첨두가 서는
   순간, 즉 **regular 세션의 바쁜 초**다. 포화를 줄이려고 늘린 폴이 **바로 그때** 밀린다.
3. **그리고 하드캡은 지금 완전히 지켜지지 않는다.** `over_limit_1s` 가 34 이고 계속 오른다.
   `docs/37` §7 은 "리미터 하드캡이 왜 1초 창을 못 지키는지"를 **미해결**로 남겼다.
   P=2 는 계획 부하를 한도의 82% (목표의 96%) 로 올린다 — **미해결 결함 위에 여유를
   전부 소진한 채 올라타는 것**이다.
4. **밀리는 것이 체결만이 아니다.** MARKET_DATA 는 tier1 `/prices` 스윕·tier3 호가·
   tier2 호가와 **같은 그룹**이다. tier2 호가는 이미 누적 52,971회 양보했다
   (`tier2_orderbook_skipped`, 2026-08-08 00:00 텔레메트리).

### 디스크는 제약이 아니다

P=2 로 회수되는 체결의 **하한**은 하루 +9,354 행 = **+0.5 MB/일**. 설령 체결 행이 두 배가
돼도 +4 MB/일이고, 랭킹 하루치(274~425 MB)의 **1% 수준**이다.
**이 결정에서 디스크는 제약이 아니다. 예산이다.**

## 8. 이 문서가 **말할 수 없는 것**

1. **몇 건이 잘렸는지 못 잰다.** API 가 원본 총 건수를 안 준다(§2). §7 의 28,530건은
   국소 체결률로 환산한 **하한**이고, 참값이 아니다.
2. **접힘의 크기를 아직 모른다.** `trades_dup_same_poll` 은 **v3 배포 이후**부터 쌓인다.
   지금 DB 에 대해 소급 계산할 방법은 없다 — 접힌 행은 이미 없다.
3. **P=2 의 실제 포화율을 모른다.** §5 는 4초 데이터에서 칸을 나눠 만든 **추정**이고,
   진짜 답은 실제로 2초로 돌려 봐야 나온다. 그리고 그 추정은 세 가지 이유로
   **낙관 쪽으로 틀린다**(§5-1).
4. **P=2 에서 실제로 걸리는 대기 시간을 모른다.** 리미터 하드캡이 몇 ms 를 먹는지
   재지 않았다 — 그러려면 라이브로 돌려야 한다.
5. **08-04 이전 시대를 같은 표에 안 넣었다.** 참고용으로만 냈고(구 설정 4s 포화 1.30%),
   tier3 정원·랭킹 타입이 달라 섞으면 안 된다.
6. **세션별로 나눠 재지 않았다.** §5 의 포화표는 네 세션을 뭉친 값이다. §6 이 보여주듯
   부하는 세션마다 4배 넘게 다르므로, **regular 세션만의 포화율은 이 표보다 나쁠 것이다.**
   재려면 별도 작업이다.

## 9. 사용자 결정 안건 — **여기서 멈춘다**

**물음: `polling.tier3_trades_s` 를 4초에서 2초로 내릴 것인가?**

| | 4초 (현행) | 2초 |
|---|---|---|
| 테이프 중 포화 몫 | 27.4% | **5.2%** (≥5.3배 개선) |
| MARKET_DATA 계획 부하 | 5.68 req/s (목표의 67%) | **8.18 req/s (목표의 96%)** |
| regular 세션 첨두 ≥ 한도 | 이미 85.4% | 더 나빠진다 (양은 미측정) |
| 미해결 하드캡 결함 위 여유 | 33% | **4%** |
| 디스크 | 4.0 MB/일 | +0.5 MB/일 (제약 아님) |
| 실제로 2초를 받는가 | — | **바쁠 때는 아니다** (대기가 걸린다) |

**중간 선택지도 있다** — 3초는 테이프 몫을 27.4% → 18.6% 로 줄이면서 계획 부하를
목표의 77% 에 둔다. 여유 23% 는 남는다.

어느 쪽이든 **§6-3 의 미해결 항목(`over_limit_1s` 가 왜 오르는가)이 먼저 풀리는 것이
순서상 맞다**고 본다. 다만 그건 이 태스크의 몫이 아니고, 판단은 사용자 몫이다.

### 재시작 시 무슨 일이 일어나는가 (실측)

**라이브 DB 의 일관 스냅샷 사본(2.21 GB, `sqlite3.Connection.backup`)에 v3 를 실제로 돌렸다.**
원본은 `mode=ro` 로만 열었고 사본은 확인 뒤 지웠다.

| | 결과 |
|---|---|
| 마이그레이션 시간 | **2 ms** (빈 테이블 DDL 이라 기존 테이블을 스캔하지 않는다) |
| `trades_snap`·`rankings_snap`·`candles_1m`·`events`·`promotions` 행수 | **변화 없음** |
| 재실행 | 멱등 (v3 유지) |
| 쓰기 경로 | `Store.record_tape_gap` 이 실제로 행을 넣는 것까지 확인 |

즉 **재시작이 곧 적용이고, 걸리는 시간은 밀리초 단위다.** 롤백이 필요하면 코드만 되돌리면
된다 — 테이블이 남아 있어도 아무도 읽지 않으므로 해가 없다. 다만 `migrations.py` 는 DB 가
코드보다 새 버전이면 거부하므로(`schema v3 is newer than supported v2`), **코드를 되돌리면
v3 DB 로는 수집기가 뜨지 않는다.** 되돌릴 때는 `meta.schema_version` 도 같이 내려야 한다.
