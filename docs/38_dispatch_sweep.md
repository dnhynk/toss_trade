소유: W5. 구현 `ops/dispatch_sweep.py`, 검증 `tests/test_ops_dispatch_sweep.py`.

## 1. 왜 — 2026-08-07 하루에 정반대 두 사고가 났다

| | `worker_done` | 실제 산출물 |
|---|---|---|

**보고와 산출물이 서로를 보증하지 않는다.** 보고가 없다고 일이 안 된 게 아니고, 보고가
왔다고 일이 남은 것도 아니다. 코디네이터가 직접 겪은 실패 유형이 최소 넷이다:

1. 워커가 보내기 전에 끊김 (08-07 W5 — 한도 프롬프트)
2. 보내놓고 커밋 안 함 (08-07 W4)
3. 런타임이 보고를 거부 (08-02 `dispatch_capability_invalid`)
4. 디스패치가 워커에 도달조차 못 함 (08-05 터미널 3개 사망, 08-03 13시간 `dispatched` + 하트비트 0)

**그리고 탐지가 순전히 운이었다.** 08-07 에 멈춘 걸 안 이유는 사용자가 *"잘 되고 있니"*
라고 물어서 코디네이터가 하트비트를 봤기 때문이다. 안 물었으면 몰랐다.

`coordination/COORDINATOR-STATE.md` 에는 이미 *"워커 보고를 믿지 말고 산출물을 직접
확인하라"* 가 있었다. **사람 규율로만 남아 있어서 그날 새어나갔다.** 이 문서의 도구는
그것을 기계가 하게 만든다 — 배선 가드(`docs/30` §3)와 같은 모양으로, **거부를 기본값으로.**

## 2. 무엇을 읽는가 (전부 실측한 것이다)

`orca orchestration` **읽기 명령만** 쓴다. 라이브 API 호출 없음.

| 축 | 소스 | 재는 것 |
|---|---|---|
| 하트비트 | `dispatch-show` 의 `last_heartbeat_at` | 마지막 생존 신호의 나이 |
| 브랜치 | 워커 워크트리의 `git log` / `git status` | 디스패치 이후 커밋·미커밋 수정 |
| 보고 매니페스트 | `task-list` 의 `result.filesModified` | 적어낸 경로가 **실제로 커밋됐는가** |
| 자격 | `dispatch-show` 의 `capability_revoked_at` / `status` | 보고 경로가 이미 닫혔는가 |

측정으로 확정한 두 가지 (2026-08-07 11:19Z):

- **`dispatched_at` 은 naive 이지만 UTC 다.** 내 디스패치가 `2026-08-07 11:16:14` 로
  찍혔고 그 시각의 실제 UTC 는 `11:19` 였다(KST 20:19). 로컬시로 읽으면 9시간이 틀어져
  모든 판정이 뒤집힌다. `last_heartbeat_at` 은 `...Z` 로 온다 — 같은 시계다.
- **워크트리 경로는 `process_incarnation` 에 들어 있다.** 형식은
  `<worktreeId>::<경로>@@<hash>:<uuid>` 이고, 예:
  `12e59c9d-...::C:/Users/dongh/orca/workspaces/toss_trade/w4-collector@@41c50d3c:4f08c390-...`.
  추측한 매핑이 아니라 런타임이 적어둔 값이다. 파싱 실패는 `unknown` 이지 "안 움직임"이 아니다.

## 4. 못 본 것을 "이상 없음"으로 말하지 않는다

`docs/31` 의 원칙 그대로다 — *"'결손 0건'이 아니라 '못 봤다'로 읽을 것."*

- 어느 축이든 판정 불가면 `unknown` 으로 **따로 세어 출력**한다. 요약 줄에 별도 카운트가 찍힌다.
- **하트비트 미발신을 죽음으로 오분류하지 않는다.** 08-07 의 W3 가 그랬다 — 일은 하고
  있는데 하트비트를 한 번도 안 보냈다. 미발신(`never`)과 정지(`stale`)는 다른 축 값이다.
- **디스패치보다 이른 하트비트**는 직전 디스패치의 낙오분이라 이 디스패치의 증거가 아니다.
  `never` 로 내린다(preamble 이 경고하는 "straggler heartbeat ... cannot mask a hung retry").
- **막 디스패치된 워커**는 `warming` 으로 유예한다. 유예가 없으면 방금 출발한 워커가 전부 빨개진다.
- 창 밖이라 안 본 닫힌 태스크 수를 출력에 찍는다. 노이즈로 제외한 미커밋 경로도 노출한다.

## 5. 문턱은 둘뿐이고 둘 다 사유가 있다

| 상수 | 값 | 사유 |
|---|---|---|
| `DEFAULT_STALE_MIN` | 15분 | 워커 계약이 "5분마다 하트비트"이므로 **연속 3회 미발신**. 5분이면 긴 툴 호출 한 번에 멀쩡한 워커가 빨개지고, 30분이면 08-07 처럼 30분 만에 멈춘 것을 못 잡는다 |
| `DEFAULT_LOOKBACK_H` | 24시간 | 매니페스트 대조가 노리는 사고는 **머지되기 전 같은 날 안에서** 새는 것이다. 머지 뒤에는 워크트리가 리셋·재사용되므로 워크트리 대조가 의미를 잃고 main 이 기록이다 |

`NOISE_SEGMENTS`(`.cache/`, `__pycache__/`, `data/` 등)는 문턱이 아니라 제외 목록이다.
사유: 이것들은 워커의 편집이 아니라 도구·수집기 산출물이라 **모든 워크트리를 항상 살아
있게 보이게 만든다** — 죽은 것을 살았다고 하는 방향의 오류라 가장 위험하다. `tests/data/`
는 워커가 만드는 픽스처일 수 있어서 `data/` 는 **리포 루트에서만** 노이즈로 본다.
그리고 **워커가 스스로 적어낸 매니페스트 경로는 노이즈에 걸려도 미커밋으로 센다** —
이 필터가 보고된 산출물을 감추면 안 된다.

**둘 다 한다: 코디네이터가 손으로도 돌고, 일일 자동화(09:30)에도 얹는다.**

```powershell

python -m ops.dispatch_sweep --run run_xxx --json
```

근거:

- **손으로 도는 것이 1순위다.** 08-07 의 두 사고는 **워커를 수거하는 순간**에 났다.
  일일 자동화는 하루 한 번이라 그 순간을 못 덮는다. 코디네이터가 워커를 닫기 직전에
  한 번 돌리는 것이 사고 지점과 시간이 맞는다.
- **자동화에도 얹는 이유는 탐지가 운이 아니게 하기 위해서다.** 08-07 에 사용자가 안
  물었으면 몰랐다. 하루 한 번은 반드시 훑는 바닥을 깔아야 한다.

### schtasks 무인 실행 — **된다. 실제로 돌려서 확인했다.**

`ops/daily_health.py` 와 같은 방식(`LogonType: Interactive`, 사용자 `dongh`)으로
일회용 작업을 등록하고 `schtasks /run` 으로 돌렸다. 결과:

- **Orca 런타임 바인딩이 필요 없다.** `orca orchestration run-use` 로 터미널을 Run 에
  묶지 않아도 `--run <id>` 를 주면 읽기 명령이 동작한다. `ORCA_*` 환경변수를 전부 제거한
  셸에서도 같은 결과였다(오케스트레이션 상태는 로컬 `orchestration.db` 에 있다).
- 확인 뒤 그 일회용 작업은 삭제했고, `tossmon-*` 예약작업 5종은 건드리지 않았다.

### 일일 자동화에 얹으려면 — **코디네이터가 넣을 한 줄** (그 파일은 코디네이터 소유라 내가 안 고쳤다)

```markdown

```

## 7. 이 도구가 **못** 보는 것

읽고 나서 안심하지 않기 위한 목록이다.

- **`never` + 브랜치 정지는 끝내 못 가른다.** 조용히 생각만 하는 워커와 죽은 워커가
  이 도구에는 똑같이 보인다. `UNKNOWN` 으로 내고 사람에게 넘긴다.
- **커미터 날짜는 다시 쓰일 수 있다.** 디스패치 이후에 rebase/amend 하면 오래된 커밋이
  "디스패치 이후"로 보인다 — 없는 진척을 있다고 말하는 방향의 오류다.
- **HEAD 만 본다.** 같은 워크트리의 다른 브랜치나 HEAD 에 없는 커밋은 안 보인다.
- **워크트리는 태스크마다가 아니라 워커마다다.** 같은 날 같은 워크트리에서 뒤에 돈
  태스크의 커밋이 앞 태스크의 "움직임"으로 읽힐 수 있다. `--lookback-hours` 를 줄이면
  겹침이 줄지만 없어지지는 않는다.
- **`ready` 상태 태스크는 안 훑는다.** 런타임이 이미 큐로 되돌린 것이라 디스패치가 아니다.
- **오래됨(`stale`)은 죽음이 아니다.** 15분은 문턱이지 사실이 아니다 — 긴 툴 호출 하나로도
  넘는다. 그래서 `PRESUMED_`(추정) 라고 이름 붙였고, 조치는 사람이 한다.
- `git log` 는 200개에서 자른다. 잘렸을 가능성이 있으면 출력에 그렇게 찍는다.

## 9. 검증 — "고쳤다"를 주장하려면 고치기 전 실패를 보여야 한다

`tests/test_ops_dispatch_sweep.py` **69건**. 그 중:

- **대조군 8건** (`test_control_*`, 그 중 6건은 아래 표의 대조군 6종을 도는 파라미터화) —
  멀쩡한 워커를 죽었다고 하면 안 된다. 하트비트 신선 /
  미발신+브랜치 커밋 / 미발신+워크트리 수정 / 방금 디스패치 / 보고+전부 커밋 / 낙오 하트비트.
  **이것이 이 스위트의 성공 기준이다.** 오분류의 대가(살아 있는 워커의 워크트리를 덮는 것)가
  탐지 실패보다 크다.

### 10.3 세 축이 어떻게 재는가 — 전부 기계적 사실이다

| 축 | 값 | 어떻게 재는가 |
|---|---|---|
| 경과 | `warming`/`normal`/`overdue`/`unknown` | `now - dispatched_at`. `warming` 문턱은 하트비트 축과 **같은 값**을 쓴다 — 두 축이 같은 "아직 이르다"를 뜻하는데 문턱이 다르면 표에서 어긋나 찍힌다 |
| 머지 | `merged`/`unmerged`/`none`/`unknown` | `git log HEAD --not main` 을 같은 창으로 다시 세서 뺀다. `merge-base --is-ancestor` 를 최신 커밋 하나에만 쓰면 안 된다 — `git log` 는 커밋 날짜 순이라 머지가 섞이면 *"최근 것이 조상이면 나머지도 조상"* 이 성립하지 않는다 |
| 소유 | `held`/`live`/`none` | 같은 워크트리에서 **나보다 나중에** 출발한 살아 있는 디스패치를 찾고, 미커밋 매니페스트 경로 중 **mtime ≥ 그 디스패치의 `dispatched_at`** 인 것을 그쪽에 넘긴다 |

기준 ref 는 `main` → `origin/main` 순으로 찾고 **하나도 못 찾으면 `unknown`** 이다.
못 찾은 것을 "안 들어갔다"로도 "들어갔다"로도 읽지 않는다.

**세 축 전부 판정을 조용하게 만드는 방향이다.** 그래서 셋 다 근거가 없을 때는 조용해지지
않는 쪽으로 기울여 두었다 — mtime 을 못 재면 소유권을 안 주고, ref 를 못 찾으면 머지로
안 세고, `dispatched_at` 이 없으면 경과는 `unknown` 이다(`docs/30` §3 의 거부 기본값).

### 10.7 이 셋을 넣고도 여전히 **못** 보는 것

- **`never` + 브랜치 `moved` + 경과 5시간은 여전히 조용하다.** 브랜치가 움직인 것은 사실이지만
  *언제* 움직였는지는 안 본다 — 4시간 전에 커밋하고 멈춘 워커가 `WORKING_SILENT` 로 나온다.
  커밋 시각을 축으로 올리면 잡히지만, 그건 "마지막 커밋 이후 경과"라는 **네 번째 문턱**이라
  근거 없이 박지 않았다.
- **소유 축은 mtime 에 기댄다.** `git checkout`·`git stash` 처럼 워커의 편집이 아닌 것도
  mtime 을 올린다. 그러면 진짜 미커밋이 살아 있는 디스패치에게 넘어갈 수 있다 — 조용해지는
  방향의 오류다. 대신 **소유자가 없으면 아무것도 안 넘어간다**는 것이 대조군 B 가 지키는 선이다.
- **머지 축은 `main` 이 최신이라고 가정하지 않는다.** 원격만 앞서 있고 로컬 `main` 이 뒤처져
  있으면 이미 머지된 것이 `unmerged` 로 나온다 — 시끄러워지는 방향이라 이쪽으로 기울여 뒀다.
- **소유는 워크트리 단위다.** 한 워크트리에 살아 있는 디스패치가 둘이면 최근 것만 주인이 된다.
  이 Run 에서는 워크트리마다 하나였다.
- `touched_paths`(브랜치 축)에는 소유를 **적용하지 않았다.** 그 축은 "워크트리가 살아 있는가"
  이고, 다음 디스패치의 편집도 그 사실 자체는 맞기 때문이다. 소유는 **매니페스트 대조에서만**
  쓴다 — 08-08 아침에 실제로 샌 지점이 거기다.
