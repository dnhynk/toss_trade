## 0. 한 문단 요약

**대조표의 `candle` 열은 우리 폴 시각을 잴 수 없다** — `candles_1m` 에는 폴 시각 컬럼이
아예 없고 `ts_ms` 는 **거래소 봉 분**이다(§2). 그래서 *"캔들은 멀쩡했다"* 는 관측이
아니라 계측기의 한계다. 폴 시각을 싣는 계측기(`rankings_snap.snap_ms` ·
`orderbook_snap.snap_ms`)로 다시 재면 **랭킹과 호가는 같은 초에 같이 멈춘다** — 08-14
정규장에 둘 다 20 초 넘게 조용한 구간이 **21 개**, 전부 13:43~14:40 UTC 안이다(§3).
그리고 프로세스 **안**의 계측기가 그것을 독립으로 확인한다: 08-14 23:11:54 · 23:27:21
KST 두 창에서 `md_peak_1s`·`chart_peak_1s`·`rank_peak_1s` 가 **셋 다 0** 이다 —
60 초 지평 안에 **어느 그룹도 한 건도 안 보냈다**(§4). **캔들도 같이 멈췄다.**
그래서 가설 2(중복 억제)는 코드에서 죽고(§6-2), 가설 3(서버가 랭킹을 안 줌)은 세 그룹
동시 정지를 설명 못 해 죽는다(§6-3). 가설 1 은 *"랭킹이 자기 그룹 예산에서 밀렸다"*
형태로는 죽고(§6-1), *"그룹과 무관하게 송신 전체가 선다"* 형태만 남는다 — 그 형태를 낼
수 있는 코드 경로는 **하나뿐이고**(`TokenManager._alock` 을 쥔 채 도는 전송 재시도,
§7-가), **그 경로를 세는 카운터가 텔레메트리에 한 번도 나온 적이 없다.** 그래서
**못 갈랐다.** 그 셋을 텔레메트리에 실었다(§9) — 다음 창은 갈린다.

## 2. ★ 먼저 계측기부터 — **`candle` 열은 폴 시각을 못 잰다**

명세 §1-2 의 대조표에서 *"캔들은 그대로다"* 가 *"일부 폴 루프만 멈췄다"* 의 근거였다.
그 열이 무엇으로 만들어지는지 스키마를 열었다.

```
CREATE TABLE candles_1m (
    symbol TEXT NOT NULL,
    ts_ms  INTEGER NOT NULL,      <- 거래소 1분봉의 봉 시각. 우리 폴 시각이 아니다
    open_u ..., high_u ..., low_u ..., close_u ..., vol_qu ...,
    PRIMARY KEY (symbol, ts_ms)
) WITHOUT ROWID
```

**폴 시각을 담는 컬럼이 없다.** `orderbook_snap` 에는 `snap_ms`(우리 시각)와
`ts_ms`(서버 시각)가 **둘 다** 있는데 `candles_1m` 에는 `ts_ms` 뿐이다.
그러므로 *"공백 구간 안에 봉 596 행이 있다"* 는 **그 구간에 폴을 했다는 뜻이 아니다** —
공백이 끝난 뒤의 폴 한 번이 그 구간을 덮는 봉들을 가져와 쓰면 같은 결과가 나온다.
캔들 폴 주기는 **110 초**(`config_sig` 의 `t2c110s`)로 공백(62~74 초)보다 **길다**.

명세가 `trades_snap.ts_ms` 에 대해 이미 같은 주의를 적었다(*"거래소 체결 시각이지 우리
폴 시각이 아니다"*). **같은 주의가 `candles_1m` 에도 그대로 걸린다.** 대조표의
`candle` 열은 지우지 말고 **"이 열로는 폴 타이밍을 못 읽는다"** 를 병기하면 된다.

**그리고 캔들은 실제로 멈췄다** — §4 의 프로세스 안 계측기가 그것을 직접 보여준다.

## 3. 랭킹과 호가는 **같은 초에** 멈춘다 (08-14 전수)

`rankings_snap.snap_ms` 와 `orderbook_snap.snap_ms` 를 합집합으로 놓고 20 초 넘는
침묵을 세면 **21 개**다. **전부 13:43:31~14:40:39 UTC 안**이다.

명세 §1-1 의 60 초 초과 4 건 안에서 호가가 얼마나 조용했나:

```
랭킹 공백                       호가 폴 수   그 안의 최장 호가 침묵
14:03:33 -> 14:04:36  62.7s          0          62.7s  (14:03:33->14:04:36)
14:10:49 -> 14:11:54  65.3s          9          60.2s  (14:10:54->14:11:54)
14:26:10 -> 14:27:22  71.6s          2          71.1s  (14:26:10->14:27:21)
14:32:41 -> 14:33:55  74.1s         18          39.4s  (14:32:53->14:33:33)
```

**1·2·3 번은 호가도 60~71 초 동안 완전히 조용하다.** 4 번만 부분적이다.
호가 쪽에서 거꾸로 세도 같은 자리가 나온다 — 호가 침묵 최장 3 건이
`14:03:20(76.1s)` · `14:26:10(71.1s)` · `14:10:54(60.2s)` 이고 그 안의 랭킹 폴은
각각 3 · **0** · **0** 건이다.

### 3-1. 느려진 것이 아니라 **섰다가 돈다**

같은 계측기로 창을 셋 비교했다.

```
창                              ob 폴 수   gaps>5s   >20s    최장    중앙 간격
08-14 14:00-14:40 (공백 구간)      2217        74     23    76.1s      0.32s
08-14 15:00-15:40 (같은 날 조용)   5146         2      0     5.8s      0.31s
08-13 14:00-14:40 (전날 같은 시각) 5826         0      0     3.6s      0.29s
```

**중앙 간격이 셋 다 같다(0.29~0.32 초).** 돌 때는 정상 속도로 돈다. 폴 수가 43% 로
준 것은 **정지 구간의 길이** 때문이지 매 폴이 느려서가 아니다.

## 4. ★ 프로세스 **안**의 계측기 — 세 그룹이 동시에 0 이었다

DB 는 "쓴 것" 만 보여준다. 송신 자체를 세는 것은 텔레메트리의 `*_peak_1s` 다 —
**60 초 지평 안 어느 1 초의 최대 송신 수**(`budget.py:617`). 이 값이 0 이면
**그 60 초 안에 그 그룹이 한 건도 안 보냈다**는 뜻이다.

2026-08-12 22:30 ~ 2026-08-15 05:00 KST 전 구간에서 셋 중 하나라도 0 인 줄은 **10 개**다.

```
2026-08-13 08:55:08  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-13 10:11:03  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-13 10:26:00  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-13 11:41:01  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-13 12:11:00  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-14 00:56:02  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-14 09:03:21  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-14 09:16:03  {md:0, chart:0, rank:0}   <- 재기동 직후 첫 줄
2026-08-14 23:11:54  {md:0, chart:0, rank:0}   <- ★ 재기동 없음
2026-08-14 23:27:21  {md:0, chart:0, rank:0}   <- ★ 재기동 없음
```

여덟은 `collector start` 직후 첫 줄이다(코디네이터가 `daily/2026-08-14.md` §9 에서 같은
성질을 이미 짚었다 — *"재기동 0.6 초 뒤 텔레메트리"*). **나머지 둘은 재기동이 없다.**
23:11:54 KST = 14:11:54 UTC, 23:27:21 KST = 14:27:21 UTC — **공백 2 번과 3 번이 끝나는
바로 그 초**다.

**이것이 이 태스크의 중심 관측이다.**

* 세 그룹은 리미터 버킷도 락도 **따로**다 (`limiter.py:190` `_bucket`, `:100` 버킷당
  `asyncio.Lock`, `:312-313` `acquire` 는 자기 버킷 락만 잡는다). 한 그룹이 굶는 것으로는
  셋이 같이 0 이 되지 않는다.
* `chart_peak_1s` 도 0 이다 → **캔들도 같이 멈췄다.** §2 가 예고한 그대로다.
* 08-12 정규장에는 이런 줄이 **하나도 없다** (그 밤 `md_peak_1s` 최솟값 9,
  `rank_peak_1s` 최솟값 3, `chart_peak_1s` 최솟값 2 — 어느 그룹도 0 에 안 닿는다).

### 4-1. 프로세스는 살아 있었다

공백 안에서 DB 쓰기가 일어난다. 공백 3 번(14:26:10~14:27:22)에 `promotions` 32 행이
들어갔다 — 다만 **전부 `14:26:10` 한 초에** 몰려 있고 그 뒤 71 초는 비어 있다.

```
gap2  promotions 쓰인 초: {14:10:49: 2, 14:10:55: 32}
gap3  promotions 쓰인 초: {14:26:10: 32}
gap4  promotions 쓰인 초: {14:32:41: 2, 14:32:51: 2, 14:33:53: 30}
```

그리고 텔레메트리 줄은 계속 나왔지만 **늦었다**. 공칭 300 초인데 실제 간격이
`335s · 345s · 315s` 다(23:06:09 · 23:11:54 · 23:27:21 KST). **10 초 틱 루프도
15~45 초 지연됐다.** 송신 정지(60~71 초)보다는 짧다.

## 5. 08-13 의 3 건은 08-14 의 33 건과 **모양이 다르다**

명세 §1-3 이 *"08-13 에 이미 3 건이 샜다 → D-21 이 유일한 원인일 수 없다"* 로 읽었다.
그 3 건 안에서 호가가 뭘 했는지 보면 **08-14 와 다르다**.

```
2026-08-13 랭킹 공백>20s        길이     그 안의 호가 폴
13:31:42 -> 13:32:07          24.1s          22
13:33:24 -> 13:33:47          22.7s          13
15:55:28 -> 15:56:06          37.7s           7
```

**셋 다 호가는 계속 돌았다.** 08-14 의 1·2·3 번(호가 0·9·2, 그중 60~71 초 완전 침묵)과
같은 현상이라고 말할 근거가 이 표에는 없다. 그리고 세 번째(15:55:28 UTC = 00:55:28 KST)는
**프로세스 사망·재기동 구간**과 겹친다 (`ALERT_20260814_005558_watch_process_dead`,
`collector start` 2026-08-14 00:56:01 KST).

> **그래서 "08-13 에 이미 있었다" 는 진술은 살아 있되 뜻이 좁아진다** — *"20 초 넘는
> 랭킹 공백"* 은 08-13 에 있었다. *"세 그룹이 동시에 60 초 서는 현상"* 은 **08-13 정규장
> 전수에 0 건**이다(§4 의 목록에 그 밤 항목이 재기동 줄뿐이다). **판정은 안 한다.**

### 5-1. 세 밤 사이에 **안 달라진 것**

| | 08-12 (공백 0) | 08-13 (3) | 08-14 (33) |
|---|---|---|---|

| `md_peak_1s` 가 천장 10 인 창 | 77/79 | 63/78 | 66/78 |
| `rank_peak_1s` 최대 | 3 | 3 | 3 |

**정원도, 포화도, 티어 전이량도 세 밤이 같다.** 08-14 만 티어 전이가 오히려 **적다**.

설정 변화로 설명되지 않는다. 08-14 만 D-21 이 붙어 있다.

## 6. 가설 셋 — 살았나 죽었나

### 6-1. 가설 1 "개장 폭주에 랭킹 폴이 밀려 굶었다" — **좁은 형태는 죽고, 넓은 형태만 남는다**

* **죽은 형태**: *"랭킹이 자기 그룹 예산·리미터에서 밀렸다."* RANKING 은 자기 버킷과
  자기 락을 가진다(`limiter.py:190`,`:100`). `rank_peak_1s` 는 세 밤 다 최대 3 이고
  RANKING 한도 근처에 간 적이 없다. 그리고 이 형태는 **호가·캔들이 같이 선 것**을
  설명하지 못한다.
* **죽은 형태**: *"MARKET_DATA 포화가 원인."* 포화도는 08-12(천장 77/79 창)가 08-14
  (66/78)보다 **더 높다**. 그 밤 공백은 0 이다.
* **남은 형태**: *"그룹과 무관하게 송신 경로 전체가 선다."* §4 가 그 모양이다.
  코드에 그런 경로가 있다 — §7-가.

### 6-2. 가설 2 "응답은 왔는데 내용이 같아 스냅을 안 남겼다" — **죽었다 (코드)**

명세가 요구한 *"내용 동일 시 건너뛰는 분기"* 를 쓰기 경로 전체에서 찾았다. **없다.**

* `loops.py:1709` — `stored += ctx.store.insert_rankings(snap_ms, page)` 를 **조건 없이**
  부른다. 앞에 내용 비교가 없다.
* `store/writer.py:140-170` — `INSERT ... ON CONFLICT(snap_ms, ranking_type, duration, rank)
  DO UPDATE SET ...`. 충돌 키에 **`snap_ms` 가 들어 있고** 그 값은 폴마다 새로 찍는
  우리 시계다(`loops.py:1698`). 그러므로 **같은 내용이어도 새 `snap_ms` 로 새 행이 된다.**
* 실패로 유실된 것도 아니다 — `rankings_write_failures` 가 08-14 정규장 전 구간 **0**.

> 즉 `distinct snap_ms` 의 공백은 **"폴을 안 했다"** 이지 **"폴했는데 안 남겼다"** 가 아니다.
> 이 문장이 §3·§4 전체의 전제다.

### 6-3. 가설 3 "서버가 그 초에 랭킹을 안 줬다" — **죽었다 (범위)**

* 서버가 랭킹만 안 준 것으로는 **호가와 캔들이 같이 선 것**을 설명 못 한다(§3·§4).
* 그리고 우리 쪽 오류 카운터가 **전부 평평하다**. 08-14 22:21~23:47 KST 의 텔레메트리
  18 창 전수에서 창별 증가분:

```
loop_errors  Δ = 0  (전 구간 36210 고정)
api_errors   Δ = 0
http_429     = 0
```

  서버가 거절했거나 응답이 깨졌으면 `api_errors` 나 `http_429` 가 움직인다. 안 움직였다.

## 7. 명세가 물은 네 가지

### (가) 랭킹 폴과 호가 폴은 같은 리미터/예산/락을 공유하는가? 캔들은 왜 다른가?

**리미터·예산은 안 나눠 쓴다. 그런데 랭킹 루프는 다른 그룹으로도 나간다.**

| 경계 | 파일:줄 |
|---|---|
| 그룹 매핑 | `api/endpoints.py:32-46` — `/rankings`→`RANKING`, `/orderbook`·`/prices`·`/trades`→`MARKET_DATA`, `/candles`→`MARKET_DATA_CHART`, `/stocks`→`STOCK` |
| 버킷·락이 **그룹당 하나** | `api/limiter.py:190` `_bucket`, `:100` `self.lock = asyncio.Lock()`, `:312-313` `acquire` 는 `b.lock` 만 잡는다 |
| 락을 **대기 중에도 쥔다** | `api/limiter.py:308-310` 주석 + `:313-328` — 같은 그룹 안에서는 직렬화된다. **다른 그룹은 못 막는다** |
| 랭킹 루프가 STOCK 으로 나감 | `collector/loops.py:1751-1755` `_resolve_universe` → `get_stocks` |
| ★ 랭킹 루프가 **MARKET_DATA** 로 나감 | `collector/loops.py:1794-1799` `_resolve_watchlist_unknowns` → `get_prices` → `after_call(GROUP_MARKET_DATA)` |
| 캔들 루프 | `collector/loops.py:2016`·`2025` — `GROUP_CHART` 하나뿐 |

그래서 **랭킹 루프는 MARKET_DATA 버킷 락에 걸릴 수 있고**(위 다섯째 줄), 그 반대도
성립한다 — 이것이 랭킹↔호가를 잇는 **그룹 경계 안의** 유일한 고리다.
**그러나 이 고리로는 캔들이 같이 선 것을 설명 못 한다** — 캔들은 CHART 하나뿐이다.

★ **그룹과 무관하게 전부를 세우는 경로는 하나다.**

```

## 8. 못 가른 것 — **이게 이 보고서에서 제일 중요한 절이다**

1. **§7-가 의 토큰·재시도 경로가 실제로 그 60~71 초를 만들었는지 못 갈랐다.**
   크기대는 맞고(≤63.5 초 vs 관측 60.2~76.1 초) 그룹 전체를 세우는 유일한 경로이지만,
   **그 경로가 돌았다는 관측이 하나도 없다.** 이유는 계측 부재다 —
   `client.counters["retries"]`·`["http_5xx"]`·`["auth_refresh"]` 는 **텔레메트리에도
   상태파일에도 나간 적이 없다.** 토큰 재발급은 성공하면 로그 한 줄도 안 남긴다.
   그래서 08-14 의 두 창을 사후에 못 읽는다. **§9 가 이것만 고친다.**
2. **76.1 초는 63.5 초보다 크다.** 최악값 계산이 관측 최댓값을 못 덮는다.
   덮으려면 `_request` 바깥의 추가 대기(예: 재시도가 두 번 겹침)를 가정해야 하는데
   **가정하지 않는다.**
3. **개장 첫 70 분 몰림을 설명 못 했다** (§7-라).
4. **08-13 의 3 건의 원인은 안 봤다.** 08-14 와 모양이 다르다는 것까지만 쟀다.
5. **이벤트루프가 막힌 것인지 송신만 막힌 것인지 못 갈랐다.** 텔레메트리 틱은
   15~45 초 늦었고 송신은 60~71 초 멈췄다 — **두 수가 다르다.** 다르다는 사실만 적는다.
