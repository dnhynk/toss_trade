## 1. 로그 패턴 경보의 창에 시간 상한이 없었다

### 무엇이 틀렸나

`ops/watchdog.ps1` 의 로그 패턴 검사 6종이 `Get-LogTail 500` **한 창을 공유**했다.
줄 수는 창이 아니다 — 그 500줄이 덮는 **시간**이 장 상태에 따라 20배 흔들린다.

### 실측 (2026-08-09, 라이브 `collector.log`)

| 시점 | 최근 500줄이 덮는 실제 시간 |
|---|---|
| 금 정규장 23:30 | 113분 |
| 금 정규장 01:00 | 77분 |
| 금 정규장 03:00 | 74분 |
| 일 09:33 (유휴) | **1,507분 = 25.1시간** |

**피해는 한 방향뿐이다.** `collector.log` 는 요청마다 찍지 않고 5분 텔레메트리 위주라
첨두에도 74분은 덮는다 — 바빠서 놓치는 일은 없다. 반대로 장이 닫히면 로그가 거의 안 늘어
한 줄이 창을 못 빠져나가고, `Raise-Alert` 의 dedup TTL 3600초와 만나 **매시간 재발화**한다:

```
원 사건 1건:  2026-08-08 08:46:12 ERROR precision drift ... 표본 '5.70891193'
결과:         ALERT_*_log_precision_drift 파일 25개 (20260808_085102 ~ 20260809_092100)
```

원 사건 자체는 사고가 아니다 — `precision_rounded=19 / precision_parsed=1,783,017 =
0.001%`. $5 짜리 주식의 소수점 7~8자리 반올림이다. **고칠 것은 경보이지 파서가 아니다.**

### 무엇을 골랐고 왜 — 상한 **180분**

- **113분(실측 최댓값)보다 59% 위**다. 그래서 **장중에는 여전히 줄 창이 먼저 걸리고
  탐지가 지금과 달라지지 않는다.** 이 여유는 장식이 아니다: `log_tape_gap` 은 **개수**로
  판정하므로(`Min = 20`) 시간 상한이 걸리면 분자가 조용히 깎인다.
- 워치독 주기(5분)의 **36배**라, 어떤 줄이든 연속 36회 검사받고 나서야 만료된다.
- 유휴 창의 1,507분을 180분으로 자른다. 한 사건이 내는 파일이 **25개 → 최대 3개**가 된다
  (T, T+60, T+120 에 발화하고 T+180 에 만료).

### 6종에 같은 상한을 쓴 근거

패턴마다 등급이 다르다(`log_auth_failure` 는 CRIT, `log_rankings_clamp` 는 INFO).
그래도 **같은 상한이 맞다**: 여섯 개 전부 "로그에 줄이 나타났다" 탐지기다. 조건이 계속되면
새 줄이 계속 찍혀 경보가 살아 있고, 새 줄이 없으면 조건이 끝난 것이다. 그러니 상한이
정하는 것은 **사건이 끝난 뒤 얼마나 더 외칠 것인가** 하나뿐이고, 그 질문은 심각도와
무관하다. 등급은 파일이 얼마나 시끄러운지를 정하지, 끝난 사건이 며칠 뉴스로 남을지를
정하지 않는다. 25시간 전 AUTH-FAILURE 는 지금 조치할 것이 없다 — 복구됐으면 로그에
남아 있고, 진행 중이면 새 줄이 있다.

### 부수 결정 두 가지

- **본문에 매치된 가장 최근 줄의 시각을 넣었다.** 예전 본문은
  `"Occurrences in the last 500 log lines: 1"` 뿐이라 파일을 열어도 25시간 전 사건인지
  방금인지 알 수 없었다.
- **날짜를 못 읽는 줄은 버리지 않고 남긴다** (트레이스백 연속 줄 등). 못 읽었다고 버리면
  진짜 경보가 조용히 사라진다 — 감당 못 할 방향이다. 대신 본문에 `undated` 로 적는다.
- **만료된 매치는 `watchdog.log` 에 `LOG-PATTERN-AGED` 로 남긴다.** 경보 파일로 만들지
  않는 이유: 그러면 방금 없앤 매시간 소음이 그대로 되살아난다.

### 라이브 전/후

```
전: ALERT_*_log_precision_drift 25개, 마지막 09:21:00 (매시간)
후: 2026-08-09 10:10:56 [watchdog] LOG-PATTERN-AGED key=log_precision_drift n=1
      older_than=180min newest=2026-08-08 08:46:12 - matched the 500-line window
      but not the time bound, so no alert.
    -> 10:21 파일 없음. 파일 수 25개에서 멈췄다.
```

덤으로 `log_tape_gap n=6` 도 만료 대상이었음이 드러났다 — 발화 문턱(20) 아래라 안 보이던
것이 이제 보인다.

### 안 고친 것

쌓여 있는 25개는 **손대지 않았다.** 고친 코드가 스스로 조용해지는지가 검증이다.

## 2. 결손 감사가 주말 창 전체를 사고로 보고했다

### 무엇이 틀렸나

일요일 리포트의 창(토 09:00 ~ 일 08:50)에는 미국장이 아예 없다. 관측 0개 →
`whole_window` 1,430분 → `ALERT_`.

`max_hole` 은 이 리포트에서 **가장 중요한 한 줄**이다 — 08-06 의 5시간 55분 정전을 옛
지표(`max_inter_poll` 1.3분) 대비 **227배** 차이로 잡아낸 지표다
(`COORDINATOR-STATE` §4.11). 그게 주말마다 늑대를 외치면 **읽는 사람이 그 줄을 건너뛰게
훈련된다.**

### 미확인이던 월요일 — 재봤다

코디네이터가 "월요일도 같은 증상일 것으로 보이나 08-03 리포트는 `max_hole` 도입 전
코드로 생성돼 확인이 안 된다"고 했다. **추측하지 않고 현재 코드로 다시 쟀다:**

| 리포트 | 요일 | n_obs | max_hole |
|---|---|---|---|
| 20260803 | **월** (창 = 일 09:00 ~ 월 08:50) | 0 | **1430.0분 [whole_window]** |
| 20260802 | 일 | 0 | 1430.0분 [whole_window] |
| 20260809 | 일 | 0 | 1430.0분 [whole_window] |

**월요일도 같은 증상이 맞다.**

### 근거를 어디서 가져왔나 — `collector.log` 의 `telemetry session=`

**`tossmon/analysis/session.py` 는 쓸 수 없다.** 그것은 **시각(time-of-day)만** 보고
요일·휴장일 개념이 없다. 실측:

```
session_of(2026-08-09 03:00 KST) -> 'regular'      # 일요일인데 정규장이라고 답한다
session_of(2026-08-10 23:00 KST) -> 'regular'
```

그것으로 고치면 버그가 그대로 남는다. 반면 **수집기는 `/market-calendar/US` 로 세션을
켜고 끄고**(`tossmon/collector/__init__.py`), 그 판정을 5분마다
`telemetry session=closed` 로 로그에 적는다. **재계산이 아니라 그때 실제로 있었던 일의
기록**이고, `gap_audit` 이 이미 읽는 파일 안에 있다(`read_log_lines`, 회전본 포함).

> `session.py` 는 **읽기만** 했고 한 줄도 고치지 않았다.
> 다만 창 자체(`daily_health.window_for`)는 KST 09:00 ~ 다음날 08:50 이고,
> **애프터 종료 경계 08:50 → 09:00 변경이 사용자 결정으로 대기 중**이다
> (`COORDINATOR-STATE` §4.11). 반영되면 창이 10분 넓어져 여기 숫자도 함께 움직인다.

### 등급은 `NOTE_` — 새 등급을 만들지 않았다

`docs/34` §3 에 **이미 같은 모양의 판정이 있다**:

> 스냅 정지 + tier2 인원 = 0 → `NOTE_` (볼 대상이 없다 — 포기한 것도 없다)

휴장은 정확히 그 모양이다. 수집할 것이 없었고, 포기한 것도 고장난 것도 없다.
`PLANNED_`(사람이 일부러 한 것)가 아닌 이유는 미국장 휴장을 아무도 하지 않았기 때문이고,
`TRADEOFF_`가 아닌 이유는 포기한 것이 없기 때문이다.

계획 정비 창과 휴장 구간이 섞여 전부 덮으면 `PLANNED_` 가 이긴다 — 사람이 한 부분이
있으면 아침에 무시해도 되는 것이 맞다.

### ★ 없는 것을 근거로 삼지 않는다 — 08-06 이 계속 잡히는 이유

**"텔레메트리가 없다"는 "장이 닫혔다"가 아니다.** 인접한 두 `closed` 관측 사이가
`CLOSED_JOIN_MAX_MS`(900초) 이내일 때만 그 구간을 닫힘으로 인정한다.

900초의 근거 — 텔레메트리 케이던스 실측(2,024줄): **p50=301s / p90=304s / p99=311s**.
900초는 3주기라 연속 2회 미발신까지 참아준다. 로그에 남은 600초 초과 침묵 4건과 대조:

| 침묵 구간 | 길이 | 이어지나 |
|---|---|---|
| 08-01 09:15 → 08-02 21:50 (수집기 정지) | 2,196분 | **아니오** |
| 08-06 03:53 → 09:41 (정전) | 348분 | **아니오** |
| 08-05 08:01 → 09:01 | 60분 | **아니오** |
| 07-31 18:05 → 18:15 | 10.1분 | 예 — 그러나 `pre` 세션이라 애초에 휴장 구간이 아니다 |

즉 **관측된 기록 안에서 이 다리가 진짜 정전을 덮은 적이 없다.**

### 창 가장자리 잔여 — 상수가 아니라 실측으로 보정

08-09 창에서 휴장 구간이 1,428분을 덮었는데도 `ALERT_` 가 남았다. 원인은 텔레메트리
**위상**이다: 창은 09:00:00 에 시작하는데 첫 관측은 09:00:11, 마지막은 08:48:18 이라
앞 0.18분 / 뒤 1.70분이 남았다. 이건 결손이 아니라 **자른 위치가 만든 것**이고,
`grade_hole` 이 폴 간격에 대해 이미 쓰는 논리와 같다.

그래서 각 휴장 구간을 바깥으로 한 주기만큼 늘리되, **그 한 주기는 상수가 아니라 그 창에서
실제로 관측된 중앙 간격**이다(상한은 이음 한계와 동일). 케이던스가 바뀌면 같이 움직이고,
정전을 덮을 만큼 커지지는 않는다.

**그리고 보정은 창 가장자리에서만 한다** — 구간 양옆에 관측이 있으면 그 시각의 상태를
우리가 이미 알고 있으므로, 그쪽으로 늘리는 것은 아는 사실을 덮는 것이다. 처음에 양방향으로
무조건 늘렸다가 **`regular` 관측 하나를 건너뛰고 두 휴장 구간이 하나로 붙는 버그**를 냈다
(§5 참조). 즉 장이 열려 있던 10분을 휴장이라고 주장했다. 테스트가 잡았고, 그 케이스를
`test_closed_spans_only_joins_adjacent_closed_observations` 에 고정해 뒀다.

있었다"* 라고 했다. 그 근거(`col_up=90,301s`, 재기동 0회)는 **08-09 의 관측**이다.
08-02 창을 직접 재보니 사실이 다르다:

```
08-01 09:15 ~ 08-02 21:50 (36.6시간)  로그 줄 1개, rankings_snap 0행, trades_snap 0행
(회전본 없음 — collector.log 단일 파일 23MB, 잘려나간 구간이 아니다)
```

사실이고, `ALERT_` 로 남는 것이 옳다. 이 도구는 "주말이면 조용히"가 아니라 **"닫혔다는
증거가 있으면 조용히"** 로 동작한다 — 그래서 08-09 는 초록이 되고 08-02 는 안 된다.

> 여부는 **코디네이터/사용자 판단**이라 내가 하지 않았다.

## 3. 예약 작업이 죽어도 아무도 몰랐다

### 무엇이 틀렸나

오늘 아침 리포트가 결번됐다. 기계는 켜져 있었고 작업은 **실행됐다가 죽었다**:

```
tossmon-dailyhealth  last=2026-08-09 08:52:01  result=3221225786 = 0xC000013A
                     = STATUS_CONTROL_C_EXIT   next=2026-08-10 08:52:00
```

`ExecutionTimeLimit=PT10M` 이므로 시간 초과(`0x41306`)가 아니다. 같은 서명이
`tossmon-collector-oneshot` 에도 있다(08-04). **경보는 하나도 울리지 않았다** —
`Get-ScheduledTaskInfo` 가 `LastTaskResult` 를 그냥 내주는데 워치독이 자기 형제 작업을
안 봤다.

### `tossmon-watchdog` 의 `result=1` — 확인했다. 정상이다.

`ops/watchdog.ps1` 맨 아래:

```powershell
if ($null -ne $restartReason) { exit 2 }
if ($problems.Count -gt 0) { exit 1 }
exit 0
```

**0 = 깨끗함 / 1 = 문제를 찾아 이미 자기 경보 파일로 보고함 / 2 = 수집기를 재기동함.**
셋 다 정상이다. 이걸 실패로 세면 거의 매 주기 발화하는 상시 경보가 되고, 게다가 워치독이
이미 낸 경보를 **이중 보고**하게 된다. 그래서 작업별 기대 결과를 따로 뒀다.

### 상시 경보가 되지 않게 한 두 가지

1. **작업별 기대 결과**: `tossmon-watchdog`·`tossmon-sentinel` 은 `{0,1,2}`, 나머지는 `{0}`.
   `267009`(실행 중)·`267011`(한 번도 안 돎)·`267012`(더 이상 실행 없음)는 판정 자체를
   보류한다 — 종료코드가 아니다.
2. **최근성 상한 24시간**: `tossmon-collector-oneshot` 은 08-04 이후 `0xC000013A` 를 계속
   달고 있고 다음 실행이 없다. 상한이 없으면 **영원히** 경보한다 — 방금 1번에서 고친 병
   그대로다. 24시간인 근거: 이 작업들 중 가장 느린 것이 일 1회(dailyhealth 08:52,
   logrotate 00:10)라, 매 실행이 최소 한 번은 판정을 받는다.

만료된 것은 `TASK-RESULT-AGED` 로 `watchdog.log` 에 남는다(경보 아님 — 1번과 같은 규칙).
등록조차 안 된 작업은 **다른 사건**이라 문구를 갈랐다.

### 라이브 전/후

```
전: 경보 0건. 코디네이터가 파일 목록을 손으로 세지 않았으면 그냥 지나갔다.
후: 2026-08-09 10:10:56 ALERT[WARN] key=task_result_tossmon_dailyhealth
      last run : 2026-08-09 08:52:01 (1h ago)
      result   : 3221225786 (0xC000013A)
      meaning  : STATUS_CONTROL_C_EXIT - killed by a console control event. Not a timeout.
      expected : 0
    TASK-RESULT-AGED task=tossmon-collector-oneshot ... age=116h ... not alerted.
    다음 주기: ALERT-SUPPRESSED key=task_result_tossmon_dailyhealth (deduped)
```

**오늘 아침의 진짜 사고를 기계가 잡았다.** 그리고 상시 경보가 되지 않는다.

### 안 고친 것 — `0xC000013A` 의 원인

**무엇이 08:52 에 콘솔을 정리했는지는 증거가 없다.** Task Scheduler 운영 로그가 비어 있어
추적 불가다. 이 항목은 **관측 추가일 뿐 원인 수정이 아니다.** 트리거를 모르는 채로
`LogonType` 을 바꾸거나 `-WindowStyle` 을 만지는 것은 증상 가리기다.

### 이 검사가 못 보는 것

**"작업이 아예 안 돌았다"는 못 잡는다** — `LastRunTime` 이 오래됐다는 것만으로는 스케줄을
모델링해야 판단할 수 있다. 그 구멍은 이미 다른 곳이 덮는다: 결번된 아침 리포트는
`run_catchup` 이 채우고, 파일의 부재 자체는 `docs/34` §9.2 가 등급으로 다룬다.

### 자기시험이 이 기계 상태에 물들던 문제

이 검사를 넣자마자 기존 대조군 5건(R1·TR1·TR2·TR4·TR5)이 빨개졌다. 샌드박스 워치독이
**이 기계의 진짜 Task Scheduler** 를 조회해 실제 `tossmon-dailyhealth` 실패를 주워온
것이다. 디스크 문턱을 이미 같은 이유로 덮어쓰고 있었으므로(`DiskSurveyGB = 0`), 같은
방식으로 `TaskInfoJson` 시험 이음매를 뒀다. **단위 시험이 돌아가는 기계의 상태에 좌우되면
그건 시험이 아니다.**

## 4. `--date` 가 기존 리포트를 말없이 덮어썼다

### 무엇이 틀렸나

`ops/daily_health.py` `main()` 이 `out.write_text(text)` 로 **무조건** 썼다. 따라잡기
경로는 `write_if_absent` 로 보호돼 있었는데(`bf81c3b`) 사람이 `--date` 로 과거 날을
재구성하는 경로만 무방비였다. 리포트 무결성이 08-06 정전을 잡아낸 근거였던 만큼
(`COORDINATOR-STATE` §4.11), 다시 만든 것이 원본을 지우면 **그 근거가 사라진다.**

### 무엇을 골랐고 왜

- **`--date` 가 있으면 기존 파일을 거부한다** (종료코드 4). 사람이 명시적으로 덮으려는
  경로는 `--force` 로 남겼다. **덮은 경우/거부한 경우 둘 다 stdout 에 찍는다.**
- **존재 확인을 재구성보다 먼저** 한다. 어차피 거부할 파일 하나 때문에 몇 분짜리 사후
  재구성을 치를 이유가 없다.
- **정시 경로(`--date` 없음)는 일부러 보호하지 않았다.** 그날 것을 늘 최신으로 갱신하는
  것이 그 경로의 일이고, 거기서 거부하면 08:52 예약 실행의 재실행이 깨진다.

## 5. 검증

| 스위트 | 결과 |
|---|---|
| `ops/watchdog_selftest.ps1` | **104 passed, 0 failed** (신규 LP 7케이스·TS 8케이스 추가) |
| `pytest -q` 전체 | **1822 passed, 1 skipped, 2 deselected** (457s) |

`closed_spans` 가 붙인 비용은 실측 **0.49초**다(`build_summary` 1회가 37.18초). 따라잡기가
7일치를 돌아도 추가 부담은 3.5초라 정시 리포트를 밀지 않는다.

**고치기 전 실패를 먼저 보였다** — 네 항목 전부 테스트를 먼저 쓰고 빨간 것을 확인했다:

- 항목 1: 워치독 자기시험 `85 passed, 7 failed` → 수정 후 `92 passed, 0 failed`.
  이때 LP2(최근 사건은 여전히 잡힌다)·LP6(개수 문턱은 안 깎인다)·LP7(날짜 못 읽는 줄은
  남긴다)은 **수정 전에도 초록**이었다 — 대조군이 먼저 서 있었다는 뜻이다.
- 항목 2: `11 failed` → 수정 후 전부 초록.
- 항목 3: TS 8건이 빨간 상태에서 시작.
- 항목 4: `3 failed / 4 passed`(통과한 4건이 대조군).

### 대조군 — 고쳐서 없애면 안 되는 것들

| 대조군 | 지키는 것 |
|---|---|
| LP2 최근 사건은 여전히 경보 | 시간 상한이 탐지기를 끄지 않았는가 |
| LP5 신선한 CRIT 은 여전히 경보 | 등급을 상한과 헷갈리지 않았는가 |
| LP6 개수 기반(`Min=20`)이 안 깎임 | 상한이 분자를 조용히 줄이지 않았는가 |
| LP7 날짜 못 읽는 줄은 유지 | 못 읽은 것을 "오래됨"으로 버리지 않았는가 |
| **08-06 의 295.5분** | **주말 예외가 진짜 정전을 삼키지 않는가** |
| 08-08(토)·08-05(수) 등급 불변 | 멀쩡한 창의 판정을 안 건드렸는가 |
| TS2·TS3 워치독 `result=1`/`2` | 정상 종료코드를 실패로 안 세는가 |
| TS5 5일 전 one-shot 실패 | 최근성 상한이 상시 경보를 막는가 |
| TS6 `267009`(실행 중) | 상태 코드를 종료코드로 안 읽는가 |
| 정시 경로가 오늘 리포트를 갱신 | 덮어쓰기 보호가 예약 실행을 안 깨뜨렸는가 |

### 이 작업 중 도구 자신에서 찾아낸 버그 2건

테스트가 없었으면 둘 다 조용히 통과했을 것들이다. 둘 다 **거짓 초록** 방향이라 더 나쁘다.

1. **가장자리 보정이 열린 세션 관측을 건너뛰었다** (§2). 휴장 구간을 양방향으로 한
   케이던스씩 늘렸더니, 사이에 낀 `regular` 관측 하나를 뛰어넘어 두 구간이 하나로
   합쳐졌다 — **장이 열려 있던 10분을 휴장이라고 주장한 것**이다. 보정을 창 가장자리로
   한정해 고쳤다.
2. **자기시험이 이 기계의 진짜 Task Scheduler 를 읽었다** (§3). 예약작업 검사를 넣자마자
   기존 대조군 5건이 빨개졌는데, 코드가 틀려서가 아니라 샌드박스가 실제 기계 상태를
   주워왔기 때문이다. 반대 방향도 마찬가지로 위험하다 — 이 기계가 마침 건강하면 진짜
   버그가 초록으로 지나간다. `TaskInfoJson` 시험 이음매로 끊었다.

## 6. 판단이 갈렸던 것 — 내가 정한 것 / 사용자·코디네이터가 정할 것

### 내가 정하고 근거를 적은 것

1. **로그 창 상한 180분** (§1). 실측 113분 위 59% 여유.
2. **6종 동일 상한** (§1). 전부 "줄이 나타났다" 탐지기라 상한이 정하는 질문이 같다.
3. **휴장 근거 = `telemetry session=`, `session.py` 아님** (§2). `session.py` 는 요일을
   모른다는 것이 실측으로 확정됐다.
4. **휴장 등급 = `NOTE_`** (§2). `docs/34` §3 의 "볼 대상이 없다" 판정과 같은 모양.
5. **이음 한계 900초 / 가장자리 보정은 실측 중앙 간격** (§2).
6. **작업 결과 최근성 상한 24시간, 워치독은 `{0,1,2}` 정상** (§3).
7. **`--date` 는 거부가 기본, 정시 경로는 보호 안 함** (§4).

### 코디네이터/사용자가 정할 것

1. **08-01 09:15 ~ 08-02 21:50 (36.6시간) 수집기 정지가 의도된 것이었나.** 의도된
   것이면 사후 `PLANNED_` 마커가 정본이고 08-02·08-03 창이 조용해진다. 아니면 그 창은
   기록된 대로 미설명으로 남는 것이 옳다. **증거가 없어 내가 정하지 않았다.**
2. **`0xC000013A` 의 트리거.** 08:52 에 무엇이 콘솔을 정리했는지 증거가 없다. 다음에
   재발하면 이제 경보가 뜨므로 **그 시각의 다른 로그와 대조할 기회**가 생긴다.
3. **애프터 종료 경계 08:50 → 09:00** (이미 대기 중인 사용자 결정). 반영되면 창이 10분
   넓어져 §2 의 숫자가 함께 움직인다.
4. **쌓인 25개 `ALERT_*_log_precision_drift`.** 지우지 않았다 — 지금은 코드가 스스로
   조용해졌다는 증거물이다. 정리 시점은 코디네이터 판단.
