# 34. 경보 등급 계약 — 트레이드오프와 사고를 가른다 (2026-08-05, 소유: W5)

> **[현행]** 소유 W5 · 2026-08-07 · ★ **등급 계약.** 언제 `PLANNED_` 를 붙일 수 있는가는 `53` 이 좁힌다
> 상태 표기의 뜻과 전수 목록: [`docs/INDEX.md`](INDEX.md)

사용자 지시: **"트레이드오프와 사고를 명확히 구분할 수 있도록 규칙 명세화를 조정해."**

계약 본문은 `ops/watchdog.ps1` 머리말(`FILE GRADE CONTRACT`)에도 같은 내용으로 들어 있다.
코드를 고치는 사람은 그쪽을, 운영을 읽는 사람은 이쪽을 본다.

## 1. 무엇이 문제였나 — 시끄러움이 아니라 **자기모순**

어젯밤(08-05) `tier2_orderbook_flat` ALERT 가 여섯 번 터졌다(00:55, 01:55, 03:10, 03:40,
04:00, 05:00). **사고가 아니었다.** tier3 가 처음으로 정원을 채우자 tier2 호가 훑기가
예산에 밀린 것이고, 그건 워치독 **자신이 다른 곳에서 "설계된 희생 순서"라고 부르는**
바로 그 동작이다.

같은 파일 안에서 20줄 떨어진 두 블록이 같은 사건을 반대로 분류하고 있었다:

```
05:00:55  ALERT_..._tier2_orderbook_flat    "...or the loop is stalled."
05:10:55  NOTE_..._tier2_orderbook_skipped  "This is the designed sacrifice order, not a fault."
```

**어느 카운터로 보느냐가 등급을 바꿨다.** 게다가 `flat` 쪽 문구는 원인 후보 셋을 나열하면서
**정작 실제 원인(예산 양보)은 후보에조차 없었다.** 아침 독자에게 "셋 중 하나인데 뭔지는
모르겠다"를 던졌고, 실제로는 넷째였다.

규칙은 이미 옳게 적혀 있었다 — `Raise-Alert` 주석이 *"이걸 `ALERT_` 로 쓰면 'ALERT_ 파일이
있으면 문제'라는 규칙이 다시 깨진다"* 고 말한다. **새 규칙을 만든 일이 아니라, 이 검사가
이미 있는 규칙을 어기고 있던 것을 고친 일이다.**

## 2. 파일 등급 4종 (사용자 결정)

| 접두사 | 뜻 | 아침에 할 일 |
|---|---|---|
| `ALERT_` | **고장.** 뭔가 잘못됐다 | 고쳐라 |
| `PLANNED_` | 사람이 일부러 한 것 | 무시 |
| `NOTE_` | 설계대로 동작한 기록 | 참고 |
| **`TRADEOFF_`** | **시스템이 무언가를 포기했다.** 고장 아님, 그러나 **사용자가 판단할 것** | 읽고 결정 |

### `TRADEOFF_` 본문의 4항목 — 하나라도 비면 트레이드오프 기록이 아니다

1. **무엇을 포기했는가** — 어느 데이터 스트림인가
2. **무엇을 위해** — 어느 쪽에 예산이 갔는가, **숫자로**
3. **얼마나 오래** — 연속 지속시간 (한 주기가 아니라 **양보가 시작된 시점부터**)
4. **얼마나** — 양보율 %, 시도 대비 스킵

### ★ 승격하지 않는다

**오래 지속돼도 `ALERT_` 로 올리지 않는다.** 근거는 사용자 판단이다: 오래 가는 것 자체는
고장이 아니라 설계가 그렇게 동작한 것이고, `ALERT_` 로 올리면 *"재시작하면 나아질 것"*
처럼 읽혀 **잘못된 대응을 부른다.** 대신 **지속시간과 양보율을 기록해 크기로 드러나게** 한다.
새 임계값을 박지 않는다.

## 3. 판별 규칙 — 원인을 가른 뒤에 등급을 정한다

근거는 **전부 이미 있는 카운터**다. `tossmon/**` 은 한 줄도 고치지 않았다.

| 관측 | 등급 | 키 |
|---|---|---|
| 스냅 정지 + `tier2_orderbook_skipped_rate` 증가 | `TRADEOFF_` (예산 양보) | `tier2_orderbook_yield` |
| 스냅 정지 + `tier2_orderbook_skipped_429` 증가 | `TRADEOFF_` (429 쿨다운, 사유를 구분해 기재) | `tier2_orderbook_yield` |
| 스냅 정지 + 두 skip 카운터 다 정지 + tier2 인원 > 0 | **`ALERT_`** (진짜 정지·오설정) | `tier2_orderbook_flat` |
| 스냅 정지 + tier2 인원 = 0 | `NOTE_` (볼 대상이 없다 — 포기한 것도 없다) | `tier2_orderbook_no_members` |

**어젯밤 실측값을 규칙에 넣어 보면**: 스냅 22,069 고정, `skipped_rate` 2,026 → 3,273 증가,
`skipped_429` 273 **고정**, tier2 인원 287~310 → **`TRADEOFF_`**. 옛 코드는 `ALERT_` 를 냈다.

### 판정마다 dedup 키를 분리했다

세 판정이 키 하나를 공유하면, **양보가 진짜 정지로 바뀌었을 때 "이건 괜찮다"고 적은 기록이
진짜 경보를 dedup 창(1시간) 동안 삼킨다.** 셀프테스트 `TC3` 가 이 경로를 지킨다.

### 인원은 `members(2)` 로 센다 — `at_least(2)` 가 아니다

tier2 호가 루프는 `members(2)` 만 돈다(tier3 는 자기 루프가 4초로 훨씬 조밀하게 본다).
텔레메트리의 `tier2` 필드는 `at_least(2)` 라 tier3 를 포함하므로, 그대로 쓰면
**tier3 가 붐빈 것을 tier2 가 있는 것으로 오독**한다. 상태 파일에서는 `tiers` 맵을
`==2` 로 세고, 로그 폴백에서는 `tier2 - tier3` 로 뺀다.

### 로그 폴백에서는 사유를 못 가른다 — 그렇게 적는다

`collector.log` 텔레메트리 줄에는 **합계 `tier2_orderbook_skipped` 만** 있다.
`rate`/`429` 분해는 `collector_state.json` 에만 있다. 그래서 로그로 읽은 경우 본문에
*"cause split unavailable from this source"* 라고 쓴다. **없는 것을 0 으로 읽지 않는다.**

### 남은 1건 — `candles_flat` (고치지 않았다, 보고만)

지시가 *"먼저 세어서 보고하라, 고칠지는 그 다음"* 이므로 손대지 않았다. 근거는 이렇다:

- `candles_1m` 카운터는 **새 봉이 들어올 때만** 오른다(`ctx.bump("candles_1m", new)`).
  그런데 `docs/31` §2 에서 실측했듯 **무체결 분에는 1분봉이 아예 없다.** 조용한 종목만
  tier2 에 남은 구간에서는 봉이 안 늘어나는 것이 정상이다.
- `run_tier2_candles` 는 `at_least(2)` 가 비면 그냥 쉰다 → 인원 0 이면 카운터 정지.
- 지금 문구는 *"the tier2 candle loop may be stalled"* 하나뿐이라 위 둘을 못 가른다.
- **다만 실측상 아직 한 번도 발화한 적이 없다** (`watchdog.log` 0회, ALERT 파일 0건).
  즉 잠재 위험이지 현재 오경보원은 아니다.
- 고치려면 tier2 인원과 "그 구간에 체결이 있었는가"를 봐야 하고, 후자는 DB 조회라
  워치독의 현재 입력(상태 파일·로그)을 넘는다. **설계 판단이 필요하므로 별도 안건.**

## 6. 아침 리포트

`ops/daily_health.py` 의 파일 집계에 `TRADEOFF_` 를 넣고 **4등급 범례를 한 줄** 붙였다.
아침 독자가 등급의 뜻을 외우고 있을 거라고 가정하지 않는다.

```
파일 등급 4종: ALERT_=고장(고쳐라) / PLANNED_=사람이 일부러(무시) / NOTE_=설계대로(참고) / TRADEOFF_=시스템이 포기함(읽고 결정)
ALERT files (창 안, 진짜 문제 — 고쳐라): N
TRADEOFF files (창 안, 시스템이 무언가를 포기함 — 고장 아님, 당신이 판단할 것): N
  ↑ 각 파일에 무엇을/무엇을 위해/얼마나 오래/얼마나 가 적혀 있다. 오래 지속돼도
    ALERT_ 로 올라가지 않는다(설계) — 크기를 보고 판단할 것.
PLANNED files (창 안, 계획된 정비 — 무시): N
NOTE files (창 안, 설계대로 동작한 기록 — 사고 아님): N
```

> 08-07 수정: 세는 기준이 **"지금부터 24시간"에서 리포트 창으로** 바뀌었다(`(창 안, …)`).
> 정시 실행에서는 두 창이 거의 겹쳐 값이 사실상 같지만, §9 의 따라잡기 분에서는 다르다 —
> 08-06 리포트에 08-07 의 `ALERT_` 가 실리면 안 된다.

### 등급을 쓰는 곳이 워치독만은 아니다 (08-05 추가)

`ops/daily_health.py` 의 **창 가장자리 구멍** 판정이 이 4등급을 그대로 쓴다
(`docs/31` §9). 구멍이 계획 창 안이면 `PLANNED_`, 밖이거나 일부만 덮이면 `ALERT_`,
그 창의 정상 폴 간격 이내면 `NOTE_` 다. **새 등급을 만들지 않았다** — 이 표에 없는
접두사가 아침에 하나라도 늘면 "아무 접두사나 붙일 수 있다"가 되고, 그러면 등급 자체가
아무 말도 안 하게 된다.

다만 아침 리포트는 **`ALERT_` 파일을 쓰지 않는다.** 이 파일은 경보가 아니라 기록이다
(경보는 `watchdog.ps1`). 등급은 본문에 글자로 찍히고, `ALERT_` 가 하나라도 있으면
`!!` 줄이 따라붙는다. 등급 이름을 공유하되 **파일을 만드는 권한은 워치독에만 둔다** —
두 곳이 `ALERT_*.txt` 를 쓰면 dedup 창이 서로를 삼킨다(§3 의 "판정마다 키를 분리했다"와
같은 이유).

계획 창을 어디서 읽는지도 여기 적어 둔다: **라이브 마커가 아니라 `PLANNED_*.txt` 의
머리말**이다. `<state_dir>/PLANNED` 는 만료 시 워치독이 지우도록 설계돼 있어서, 아침
리포트가 도는 시점엔 이미 없는 것이 정상이다. 즉 **이 등급 체계가 남긴 파일 자체가
사후 조회의 유일한 근거**가 된다 — 머리말 형식(`window until ...` / `reason:`)을
바꾸면 `gap_audit.planned_windows()` 가 조용히 아무것도 못 찾는다. 바꾸려면 같이 고쳐라.

## 7. 새 검사를 추가하는 사람에게 (강제 사항)

**등급을 먼저 정하고, 무엇이 고장과 설계를 가르는지 적어라.**

검사가 **부재**(카운터가 안 오름, 나이가 한계를 넘음)로 발화한다면 반드시 물어라:

> **수집기가 이 부재를 일부러 만들 수 있는가?**

- **예** → 그것을 증명하는 카운터를 읽고 그에 맞춰 등급을 정하라. 안 그러면 **원인을
  모른 채 현상에 등급을 매기는 것**이고, 그게 08-05 밤 여섯 건의 오경보가 나온 경로다.
- **아니오** → 사유를 여기 §4 표에 한 줄 추가하고 `ALERT_` 로 둬라.

`TRADEOFF_` 를 쓸 거라면 4항목을 **전부** 채워라. 채울 수 없는 항목이 있으면 그건
트레이드오프 기록이 아니다 — 못 채우는 이유를 본문에 적어라.

## 9. 등급은 이름이 아니라 **본문이 시키는 행동**이다 (08-07 추가)

§1~§8 은 "이 파일에 어느 접두사를 붙일 것인가"를 다뤘다. 08-06 이 그 다음 층을 보여줬다:
**접두사가 맞아도 본문이 틀린 행동을 시키면 등급은 아무 일도 안 한 것과 같다.** 그리고
그보다 한 층 더 아래: **파일이 아예 없으면 등급을 붙일 대상 자체가 없다.**

### 9.1 같은 `ALERT_` 안에서도 사유 계열이 다르면 판단 근거가 다르다

`data/ALERT_20260806_094100_watch_process_dead.txt` 원문:

```
Watchdog detected: both_dead (session=unknown age_min=346.7 sup=0 col=0). Restarting via ...
  session       : regular  [NOT TRUSTED - older than the 300s trust window ...]
WAS THIS RESTART JUSTIFIED? Read the evidence above:
  - if 'session' is marked NOT TRUSTED, ... -> the restart was probably wrong,
    and that is a watchdog defect worth reporting.
```

`sup=0 col=0` 이다 — 감독자도 수집기도 **실제로 없었다.** 재시작은 옳았고 09:41 에 수집이
되살아났다. 그런데 첫 불릿이 발화해서 아침 독자에게 *"아마 틀렸다, 워치독 결함을 찾아라"*
라고 말했다. 등급(`ALERT_`)도 맞고 사유 이름(`process_dead`)도 맞는데 **본문이 없는 결함을
쫓게 한다.** 08-04 의 거짓 CRIT 을 막으려고 붙인 문구가, 계열이 다른 사건에 그대로 붙어
반대 방향의 오독을 만들었다.

재시작 사유는 두 계열이고 **판단 근거가 서로 다르다**:

| 계열 | 사유 (`ops/watchdog.ps1`) | 무엇이 판단 근거인가 |
|---|---|---|
| 프로세스 부재 | `process_dead`(855) `supervisor_dead`(859) `collector_dead`(867) | **`sup`/`col` 카운트.** 둘 다 0이면 재시작은 옳다 — 없는 것을 세션 신선도로 변호할 수 없다 |
| 진행 정지 | `log_stale`(899) `counters_frozen`(916) `ranking_snap_never`(1212) `ranking_snap_stalled`(1228) `auth_failures`(1272) `token_dead`(1508) | **세션 신선도.** 08-04 거짓 CRIT 이 정확히 이 계열이었다 |

그래서 자기평가 문구를 계열별로 갈랐다(`ops/watchdog.ps1` 의 `$judgeLines`). 프로세스 부재
쪽은 `sup`/`col` 이 근거임을 적고, **`sup` 이나 `col` 이 0이 아닌데 재시작했다면 그것이
결함**이라고 뒤집어 적는다. 진행 정지 쪽 문구는 **한 글자도 안 바꿨다** — 08-04 에 비싸게
얻은 것이다.

> **새 재시작 사유를 추가하는 사람에게(강제):** 사유를 어느 계열에 넣을지 먼저 정하고,
> `ops/watchdog.ps1` 의 계열 목록(`@("process_dead", "supervisor_dead", "collector_dead")`)에
> 넣을지 말지를 명시적으로 결정하라. 기본값(진행 정지 문구)이 조용히 붙는다.

검사는 `ops/watchdog_selftest.ps1` 이 한다. 예전엔 T1 이 문구의 **존재**만 봤다 — 08-06 에도
그 문구는 존재했다. 이제 **사유별로 맞는 문구인지**를 본다: T3(프로세스 부재)은
`PROCESS COUNTS ... sup=0 col=0` 을 요구하고 `probably wrong` 을 금지, T1(진행 정지)은 정확히
그 반대. 공용 문구로 되돌리는 변이를 넣으면 T3 3건이 깨진다(78 passed / 3 failed → 81/0).

### 9.2 파일의 **부재**도 등급이다 — 그리고 사고는 자기 자신을 감춘다

`data/daily_health_20260806.txt` 가 **없었다.** 기계가 2026-08-06 03:46 비정상 종료 →
09:36 재부팅이라 예약 시각 08:52 에 꺼져 있었고, 작업 스케줄러는 놓친 실행을 따라잡지 않는다.

그런데 그 결번된 창이 하필 이 프로젝트 최대 공백이 난 창이었다. 수동 재실행해서야 보였다:

```
window (KST): 2026-08-05 09:00 ~ 2026-08-06 08:50
  max_hole       : 295.5min  [trailing_hole]  (2026-08-06 03:54:30 -> 08:50:00)
  max_inter_poll :   1.3min
```

**사고가 자기 자신을 감춘다** — 기계를 죽인 사고가 그 사고를 드러낼 리포트도 같이 죽인다.
`ALERT_` 를 아무리 잘 등급 매겨도, 그것을 **모아 보여주는 한 장이 결번되면** 아침에 아무
일도 없었던 것처럼 보인다. 무등급(파일 없음)이 조용히 무사고로 읽히는 것이 §1 의
"자기모순"과 같은 종류의 실패다.

`ops/daily_health.py` 가 다음 성공 실행에서 빠진 날을 채운다(`run_catchup`). 규칙:

- **기준은 파일의 존재**다. 별도의 "마지막 실행" 상태 파일을 두지 않는다 — 상태 파일은
  기계가 죽을 때 같이 죽거나 산출물과 어긋나지만, 산출물 자체는 어긋날 수 없다.
- **이미 있는 파일은 안 건드린다**(멱등). 아침 리포트는 기록이고, 뒤늦은 실행이 과거를
  다시 쓰면 안 된다.
- 범위는 **가장 오래된 리포트의 다음 날 ~ 어제** 안의 결번만. 기록열을 과거로 소급
  확장하지 않는다(수집기가 없던 날에 "0건" 파일을 찍어내지 않기 위해).
- 상한은 `daily_health.catchup_days`(기본 7일). 근거: 사후 재구성이 읽는 `collector.log` 의
  회전 보존이 `log_retention_days`(14)일이라 그 절반이면 `[체결 tape gap]` 절이 아직 살아
  있고, 1일 상한은 주말을 낀 다일 정전을 못 넘긴다. 하루 재구성 비용 실측 ≈12초
  (2GB DB, 3창 37초). **상한 밖이라 포기한 결번은 stdout 에 목록으로 찍는다** — 조용히
  자르는 상한은 "다 봤다"로 읽힌다.
- 따라잡은 파일은 제목에 `[CATCH-UP]` 이 붙고, **사후 재구성이 못 보는 것을 스스로 적는다**:
  `[체결 tape gap]`·`config_sig`·재기동 횟수는 로그 회전 보존기간 밖을 못 본다("결손 0건"이
  아니라 **"못 봤다"**). `last telemetry` 절은 싣지 않는다 — 그 꼬리는 생성 시각의 상태다.
- 창이 통째로 빈 날(기계가 하루 종일 꺼져 있던 날)에도 **파일은 남긴다.** 사유는
  판정하지 않는다(기계 꺼짐 / 수집기 부재 / 휴장 / DB 결손을 이 도구는 못 가른다).
  **파일의 존재는 "봤다"는 뜻이지 "수집됐다"는 뜻이 아니다.**

실측(2026-08-07 09:55, `python -m ops.daily_health`): `catch-up: made=2 ['20260802',
'20260806']`. 08-06 분에 위의 295.5분 공백이 그대로 찍혔고, 값은 코디네이터가 수동
재실행한 `data/gap_audit_20260806_recovered.txt` 와 일치한다(A=221 / B=83 / C=139).
두 번째 실행은 `made=0` 이고 두 파일의 md5 가 안 바뀐다.

## 10. `NOTE_<stamp>_restart_sample.txt` — 재기동 직전 표본 (2026-08-22 추가)

`ops/watchdog.ps1` 은 수집기를 죽이기 **직전에** `data/NOTE_<stamp>_restart_sample.txt` 를
남긴다. 스택(py-spy) · 프로세스 트리 · IO/핸들/스레드 2회 측정 델타 · 그 재기동을 결정한
판단값(`age_min`·`col_up`·`rank_age`·`t2book`)이 한 파일에 들어간다.

**등급이 `NOTE_` 인 이유:** 같은 사건의 고장은 이미 `ALERT_*_watch_<reason>.txt` 로 찍힌다.
이 파일은 그 경보에 붙는 **증거**이지 두 번째 고장이 아니다. `ALERT_` 로 세면 아침의
"ALERT 0건이면 무사" 가 다시 깨진다. 경보 본문에는 표본 파일 이름이 한 줄 실린다.

**`Raise-Alert` 를 통과시키지 않는다 — 고치지 마라.** `Raise-Alert` 는 키 단위로 몇 시간을
dedup 한다. 오늘 아침에 재기동이 한 번 있었다는 이유로 다음 재기동의 표본이 억제되면,
이 표본을 만든 이유 자체가 사라진다(재현 기회는 08-19·08-21 두 번뿐이었고 두 번 다
놓쳤다). 그래서 직접 쓴다. `PLANNED` 창 판정도 적용하지 않는다 — 증거 수집은 계획
정비 중에도 똑같이 유효하다.

**자가 복구보다 우선하지 않는다.** 표본 수집 전체가 `try/catch` 와 `-RestartSampleBudgetS`
(기본 20s) 안에 있고, 실패하든 예산을 넘든 `RESTART` 는 그대로 진행된다. 호출자는 반환값을
보지 않는다. 실패는 `data/watchdog.log` 의 `restart-sample:` 줄에만 남는다.

**세 경로 모두에서 뜬다** — `kill`(실제 재기동), `dryrun`(`-DryRunRestart`),
`budget_exhausted`(재기동 포기). 파일 머리말 `mode:` 가 어느 쪽인지 말한다. 뒤의 두 경로는
아무것도 죽이지 않으므로 수집 공백이 0 이고, `budget_exhausted` 는 멈춘 프로세스가
**살아남는** 유일한 경로라 사람이 파일과 실물을 대조할 수 있다.

**회전에서 지워지지 않는다:** `ops/rotate_logs.py` 는 `*.log` 와 `*.log.*.gz` 만,
워치독의 `Invoke-Reclaim` 은 `data/` 의 `*.gz` 만 건드린다. `*.txt` 는 둘 다 대상이 아니다.

### 10-1. 스택 대상은 **자손까지**이고, 순서가 곧 예산이다 (2026-08-22 2차)

`<repo>/.venv/Scripts/python.exe` 는 인터프리터 복사본이 아니라 **파이썬 런처**(`py.exe`,
255KB)다. 진짜 인터프리터를 **자식으로 다시 띄우고**, 그 자식의 `ExecutablePath` 는
`...\Programs\Python\Python313\python.exe` 라 `-ExeLike`(`<repo>\.venv\*`) 를 통과하지
못한다. 명령줄은 **둘이 똑같다**. 라이브 사슬 넷 중 워치독이 `sup=1 col=1` 로 세는 이유가
이것이다 — 세는 대상이 런처 스텁뿐이다.

스텁은 파이썬 상태를 하나도 안 들고 있다: py-spy 가 `Failed to find python version from
target process` 를 낸다. **이건 권한 거부가 아니다**(`os error 5` 가 아니다). 그래서
`Get-SampleProcs` 는 씨앗(= `-ExeLike` 통과분)에서 **부모-자식 폐포**를 취한다. 이걸 되돌려
씨앗만 쓰면 §[3] 은 영원히 쓸모 있는 스택을 못 담는다. 폐포는 `taskkill /T` 가 지우는 트리와
같은 집합이기도 하다 — 표본이 덮는 범위와 재기동이 지우는 범위가 일치한다.

**순서 규칙**: 수집기 패턴 → 감시자 패턴 → 나머지, 각 등급 안에서 스레드 수 내림차순,
그다음 핸들 수, 그다음 PID. WMI 는 대략 PID 순으로 돌려주는데 그러면 먼저 뜬 스텁이 앞에
온다. 개당 상한이 8 초라 **매달린 트리에서는 앞의 것이 예산을 다 먹고 정작 필요한 스택을
못 뜬다.** 스레드 수는 **정렬 키이지 필터가 아니다** — "1 스레드면 스텁"은 오늘의 관측이지
계약이 아니고, 아무것도 버리지 않는다(사슬이 어디서 끊겼는지는 스텁이 있어야 보인다).

`ops/watchdog_selftest.ps1` 의 `RS1`~`RS5` 가 이 절을 지킨다. 특히 **`RS1`** 은 표본 수집이
실패해도 `RESTART` 가 진행되는지를 본다 — 그 계약을 지키는 것은 `try/catch` 의 위치뿐이라
다음 사람이 옮기면 조용히 깨진다.
