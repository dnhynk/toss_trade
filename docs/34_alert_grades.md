# 34. 경보 등급 계약 — 트레이드오프와 사고를 가른다 (2026-08-05, 소유: W5)

사용자 지시: **"트레이드오프와 사고를 명확히 구분할 수 있도록 규칙 명세화를 조정해."**

계약 본문은 `ops/watchdog.ps1` 머리말(`FILE GRADE CONTRACT`)에도 같은 내용으로 들어 있다.
코드를 고치는 사람은 그쪽을, 운영을 읽는 사람은 이쪽을 본다.

---

## 1. 무엇이 문제였나 — 시끄러움이 아니라 **자기모순**

어젯밤(08-05) `tier2_orderbook_flat` ALERT 가 여섯 번 터졌다(00:55, 01:55, 03:10, 03:40,
04:00, 05:00). **사고가 아니었다.** tier3 가 처음으로 정원을 채우자 tier2 호가 훑기가
예산에 밀린 것이고, 그건 워치독 **자신이 다른 곳에서 "설계된 희생 순서"라고 부르는**
바로 그 동작이다.

같은 파일 안에서 20줄 떨어진 두 블록이 같은 사건을 반대로 분류하고 있었다:

```
05:00:55  ALERT_..._tier2_orderbook_flat    "...or the loop is stalled."
05:10:55  NOTE_..._tier2_orderbook_skipped  "This is the designed sacrifice order, not a fault."
```

**어느 카운터로 보느냐가 등급을 바꿨다.** 게다가 `flat` 쪽 문구는 원인 후보 셋을 나열하면서
**정작 실제 원인(예산 양보)은 후보에조차 없었다.** 아침 독자에게 "셋 중 하나인데 뭔지는
모르겠다"를 던졌고, 실제로는 넷째였다.

규칙은 이미 옳게 적혀 있었다 — `Raise-Alert` 주석이 *"이걸 `ALERT_` 로 쓰면 'ALERT_ 파일이
있으면 문제'라는 규칙이 다시 깨진다"* 고 말한다. **새 규칙을 만든 일이 아니라, 이 검사가
이미 있는 규칙을 어기고 있던 것을 고친 일이다.**

## 2. 파일 등급 4종 (사용자 결정)

| 접두사 | 뜻 | 아침에 할 일 |
|---|---|---|
| `ALERT_` | **고장.** 뭔가 잘못됐다 | 고쳐라 |
| `PLANNED_` | 사람이 일부러 한 것 | 무시 |
| `NOTE_` | 설계대로 동작한 기록 | 참고 |
| **`TRADEOFF_`** | **시스템이 무언가를 포기했다.** 고장 아님, 그러나 **사용자가 판단할 것** | 읽고 결정 |

### `TRADEOFF_` 본문의 4항목 — 하나라도 비면 트레이드오프 기록이 아니다

1. **무엇을 포기했는가** — 어느 데이터 스트림인가
2. **무엇을 위해** — 어느 쪽에 예산이 갔는가, **숫자로**
3. **얼마나 오래** — 연속 지속시간 (한 주기가 아니라 **양보가 시작된 시점부터**)
4. **얼마나** — 양보율 %, 시도 대비 스킵

### ★ 승격하지 않는다

**오래 지속돼도 `ALERT_` 로 올리지 않는다.** 근거는 사용자 판단이다: 오래 가는 것 자체는
고장이 아니라 설계가 그렇게 동작한 것이고, `ALERT_` 로 올리면 *"재시작하면 나아질 것"*
처럼 읽혀 **잘못된 대응을 부른다.** 대신 **지속시간과 양보율을 기록해 크기로 드러나게** 한다.
새 임계값을 박지 않는다.

## 3. 판별 규칙 — 원인을 가른 뒤에 등급을 정한다

근거는 **전부 이미 있는 카운터**다. `tossmon/**` 은 한 줄도 고치지 않았다.

| 관측 | 등급 | 키 |
|---|---|---|
| 스냅 정지 + `tier2_orderbook_skipped_rate` 증가 | `TRADEOFF_` (예산 양보) | `tier2_orderbook_yield` |
| 스냅 정지 + `tier2_orderbook_skipped_429` 증가 | `TRADEOFF_` (429 쿨다운, 사유를 구분해 기재) | `tier2_orderbook_yield` |
| 스냅 정지 + 두 skip 카운터 다 정지 + tier2 인원 > 0 | **`ALERT_`** (진짜 정지·오설정) | `tier2_orderbook_flat` |
| 스냅 정지 + tier2 인원 = 0 | `NOTE_` (볼 대상이 없다 — 포기한 것도 없다) | `tier2_orderbook_no_members` |

**어젯밤 실측값을 규칙에 넣어 보면**: 스냅 22,069 고정, `skipped_rate` 2,026 → 3,273 증가,
`skipped_429` 273 **고정**, tier2 인원 287~310 → **`TRADEOFF_`**. 옛 코드는 `ALERT_` 를 냈다.

### 판정마다 dedup 키를 분리했다

세 판정이 키 하나를 공유하면, **양보가 진짜 정지로 바뀌었을 때 "이건 괜찮다"고 적은 기록이
진짜 경보를 dedup 창(1시간) 동안 삼킨다.** 셀프테스트 `TC3` 가 이 경로를 지킨다.

### 인원은 `members(2)` 로 센다 — `at_least(2)` 가 아니다

tier2 호가 루프는 `members(2)` 만 돈다(tier3 는 자기 루프가 4초로 훨씬 조밀하게 본다).
텔레메트리의 `tier2` 필드는 `at_least(2)` 라 tier3 를 포함하므로, 그대로 쓰면
**tier3 가 붐빈 것을 tier2 가 있는 것으로 오독**한다. 상태 파일에서는 `tiers` 맵을
`==2` 로 세고, 로그 폴백에서는 `tier2 - tier3` 로 뺀다.

### 로그 폴백에서는 사유를 못 가른다 — 그렇게 적는다

`collector.log` 텔레메트리 줄에는 **합계 `tier2_orderbook_skipped` 만** 있다.
`rate`/`429` 분해는 `collector_state.json` 에만 있다. 그래서 로그로 읽은 경우 본문에
*"cause split unavailable from this source"* 라고 쓴다. **없는 것을 0 으로 읽지 않는다.**

## 4. 전수 조사 — 같은 모양이 또 있는가

*"스트림이 멈췄다"* 로 경보하는 검사(= **부재(absence) 가족**)를 전부 세었다.
`Raise-Alert` 호출 지점 27곳, 표 기반 로그 패턴 6종, 쓰기실패 루프 3종 →
**경보 키 37종**(이번에 2종 신설 포함).

그중 **부재로 발화하는 검사는 12개**다:

| # | 검사 | 설계된 원인이 존재하는가 | 원인을 가르는가 |
|---|---|---|---|
| 1 | `ranking_snap_stalled` | 예 (폐장·세션 방금 열림·수집기 방금 기동) | **가른다** (08-04 수정) |
| 2 | `counters_frozen` (재기동 사유) | 예 (폐장) | **가른다** (폐장 분기) |
| 3 | `tier2_orderbook_flat` | 예 (예산 양보·429·무인원) | **가른다** ← **이번 수정** |
| 4 | `candles_flat` | 예 (무체결 분엔 봉이 없다 / tier2 인원 0) | **안 가른다** ← **남은 1건** |
| 5 | `no_telemetry` | 아니오 | 해당 없음 |

| 8 | `watchdog_silent` | 아니오 | 해당 없음 |
| 9 | `watchdog_heartbeat_missing` | 아니오 | 해당 없음 |
| 10 | `sentinel_silent` | 아니오 | 해당 없음 |
| 11 | 프로세스 사망(`both_dead`/`supervisor_dead`/`collector_dead`) | 아니오 | 해당 없음 |

**결과: 12개 중 4개가 설계된 원인에 오염될 수 있고, 그중 3개는 가르고 1개는 안 가른다.**

### 남은 1건 — `candles_flat` (고치지 않았다, 보고만)

지시가 *"먼저 세어서 보고하라, 고칠지는 그 다음"* 이므로 손대지 않았다. 근거는 이렇다:

- `candles_1m` 카운터는 **새 봉이 들어올 때만** 오른다(`ctx.bump("candles_1m", new)`).
  그런데 `docs/31` §2 에서 실측했듯 **무체결 분에는 1분봉이 아예 없다.** 조용한 종목만
  tier2 에 남은 구간에서는 봉이 안 늘어나는 것이 정상이다.
- `run_tier2_candles` 는 `at_least(2)` 가 비면 그냥 쉰다 → 인원 0 이면 카운터 정지.
- 지금 문구는 *"the tier2 candle loop may be stalled"* 하나뿐이라 위 둘을 못 가른다.
- **다만 실측상 아직 한 번도 발화한 적이 없다** (`watchdog.log` 0회, ALERT 파일 0건).
  즉 잠재 위험이지 현재 오경보원은 아니다.
- 고치려면 tier2 인원과 "그 구간에 체결이 있었는가"를 봐야 하고, 후자는 DB 조회라
  워치독의 현재 입력(상태 파일·로그)을 넘는다. **설계 판단이 필요하므로 별도 안건.**

## 6. 아침 리포트

`ops/daily_health.py` 의 파일 집계에 `TRADEOFF_` 를 넣고 **4등급 범례를 한 줄** 붙였다.
아침 독자가 등급의 뜻을 외우고 있을 거라고 가정하지 않는다.

```
파일 등급 4종: ALERT_=고장(고쳐라) / PLANNED_=사람이 일부러(무시) / NOTE_=설계대로(참고) / TRADEOFF_=시스템이 포기함(읽고 결정)
ALERT files (24h, 진짜 문제 — 고쳐라): N
TRADEOFF files (24h, 시스템이 무언가를 포기함 — 고장 아님, 당신이 판단할 것): N
  ↑ 각 파일에 무엇을/무엇을 위해/얼마나 오래/얼마나 가 적혀 있다. 오래 지속돼도
    ALERT_ 로 올라가지 않는다(설계) — 크기를 보고 판단할 것.
PLANNED files (24h, 계획된 정비 — 무시): N
NOTE files (24h, 설계대로 동작한 기록 — 사고 아님): N
```

### 등급을 쓰는 곳이 워치독만은 아니다 (08-05 추가)

`ops/daily_health.py` 의 **창 가장자리 구멍** 판정이 이 4등급을 그대로 쓴다
(`docs/31` §9). 구멍이 계획 창 안이면 `PLANNED_`, 밖이거나 일부만 덮이면 `ALERT_`,
그 창의 정상 폴 간격 이내면 `NOTE_` 다. **새 등급을 만들지 않았다** — 이 표에 없는
접두사가 아침에 하나라도 늘면 "아무 접두사나 붙일 수 있다"가 되고, 그러면 등급 자체가
아무 말도 안 하게 된다.

다만 아침 리포트는 **`ALERT_` 파일을 쓰지 않는다.** 이 파일은 경보가 아니라 기록이다
(경보는 `watchdog.ps1`). 등급은 본문에 글자로 찍히고, `ALERT_` 가 하나라도 있으면
`!!` 줄이 따라붙는다. 등급 이름을 공유하되 **파일을 만드는 권한은 워치독에만 둔다** —
두 곳이 `ALERT_*.txt` 를 쓰면 dedup 창이 서로를 삼킨다(§3 의 "판정마다 키를 분리했다"와
같은 이유).

계획 창을 어디서 읽는지도 여기 적어 둔다: **라이브 마커가 아니라 `PLANNED_*.txt` 의
머리말**이다. `<state_dir>/PLANNED` 는 만료 시 워치독이 지우도록 설계돼 있어서, 아침
리포트가 도는 시점엔 이미 없는 것이 정상이다. 즉 **이 등급 체계가 남긴 파일 자체가
사후 조회의 유일한 근거**가 된다 — 머리말 형식(`window until ...` / `reason:`)을
바꾸면 `gap_audit.planned_windows()` 가 조용히 아무것도 못 찾는다. 바꾸려면 같이 고쳐라.

## 7. 새 검사를 추가하는 사람에게 (강제 사항)

**등급을 먼저 정하고, 무엇이 고장과 설계를 가르는지 적어라.**

검사가 **부재**(카운터가 안 오름, 나이가 한계를 넘음)로 발화한다면 반드시 물어라:

> **수집기가 이 부재를 일부러 만들 수 있는가?**

- **예** → 그것을 증명하는 카운터를 읽고 그에 맞춰 등급을 정하라. 안 그러면 **원인을
  모른 채 현상에 등급을 매기는 것**이고, 그게 08-05 밤 여섯 건의 오경보가 나온 경로다.
- **아니오** → 사유를 여기 §4 표에 한 줄 추가하고 `ALERT_` 로 둬라.

`TRADEOFF_` 를 쓸 거라면 4항목을 **전부** 채워라. 채울 수 없는 항목이 있으면 그건
트레이드오프 기록이 아니다 — 못 채우는 이유를 본문에 적어라.

## 8. 경계 / 하지 않은 것

- **판정하지 않았다.** 이 문서는 분류 규칙이지 *"tier2 호가를 포기해도 되는가"* 에 대한
  답이 아니다. 그 판단은 사용자 몫이고 `COORDINATOR-STATE.md` §4.9-7 에 올라가 있다.
- **`tossmon/**` 무수정.** 필요한 카운터가 전부 이미 나오고 있었다.
- **수집기 무접촉** — 재시작·설정 변경·라이브 API 호출 0.
- **어젯밤 `ALERT_20260805_*_tier2_orderbook_flat.txt` 6건은 그대로 뒀다.** 과거 기록이고,
  새 규칙은 앞으로 나올 것에만 적용된다.
- `candles_flat`(§4) 은 **보고만 하고 고치지 않았다.**
