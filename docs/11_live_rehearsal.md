## 1. (A-2) 1분봉 보관 경계 정밀 이분탐색 — `확인됨`

W1은 1024일 hit / 2048일 miss 까지만 좁혔다(docs/06 §2). 대형주 1 + 소형주 1을 하루 단위로
이분탐색했다.

### 1-1. AAPL (대형주)

- **경계: 1702일 전 = hit, 1703일 전 = miss** (앵커: 2026-07-30T20:50:00+09:00 기준 최신봉)
- 콜 수: 10 (이미 확인된 1024/2048 힌트를 재확인 없이 바로 재사용해 절약)
- 1702일 전 봉 timestamp: `2021-12-01T21:30:00.000+09:00`(ms=1638359400000) — 진짜 1분봉 그리드인지는
  W1이 이미 확인한 방식과 동일 소스이므로 별도 재검증 생략(비용 절감).
- **W1의 "2.8년 이상"이라는 보수적 결론보다 실제로는 약 4.66년(≈1702일)** — 백필 계획(docs/03 §1-A)의
  규모 산정을 상향 조정할 수 있는 근거.

### 1-2. SNTI (소형주) — ⚠️ 대형주와 크게 다름

- **경계: 320일 전 = hit, 321일 전 = miss** (앵커: SNTI 자체의 최신봉, 2026-07-30T14:32:00+09:00 —
  AAPL과 다른 시각인 이유: SNTI는 그 시각 이후 체결이 없어 최신봉이 더 과거임)
- 콜 수: 대괄호 탐색 2 + 이분 8 = 10
- **약 320일(≈10.5개월)로 AAPL의 1702일보다 훨씬 짧다.** 320일 전 봉: `2025-09-14` 근방
  (ms=1757721240000).
- **설계 함의 (중요)**: 백필 계획이 "1분봉은 1024일 이상 보관되니 전 종목 균일하게 백필 가능"을
  전제한다면 이 전제가 소형주에서 깨진다. 이유는 확인하지 못했다(신규상장/재상장, 혹은 유동성이
  낮은 종목 자체의 보관 정책 차이, 혹은 우연히 이 종목의 사정 — 추측 금지, 다른 소형주로 재검증
  필요). **백필 규모 산정 시 종목별로 실제 depth를 먼저 프로브하고 가정하지 말 것**을 권고한다.

### 1-3. 종합

| 종목 | 시총구분 | 경계(hit/miss, 일) | 비고 |
|---|---|---|---|
| AAPL | 대형 | 1702 / 1703 | W1 대비 훨씬 깊음 |
| SNTI | 소형 | 320 / 321 | AAPL의 1/5 수준 |

## 2. (A-3) 1분봉 timestamp 시작/끝 판정 — `부분확인` (AAPL 약한 신호, 소형주는 §3 이슈로 중단)

방법(코디네이터 지시, 2026-07-30): `/trades` 체결 시각을 `/candles` 각 봉의 `vol_qu`와 대조해
어느 시간창(`[T,T+60s)` 시작 가설 vs `(T-60s,T]` 끝 가설)의 체결량 합이 봉의 거래량과 더 가까운지로
판정.

### 2-1. AAPL — 약한 신호, 결론 보류

- `/trades count=50` 이 **단 110초**(20:47:32~20:49:22)만 커버했다 — AAPL이 현재 매우 활발히
  거래되고 있어(한 봉에 vol_qu가 최대 202,020 주 상당) 50건으로는 한 분(1분)도 온전히 못 덮는다.
  docs/06 §4의 "50건이 10분치"라는 프리마켓 관측과 달리, **유동성이 높으면 50건 샘플이 오히려
  분 단위 대조에 못 미친다** — 이 자체가 흥미로운 함의다(A2 §2 "테이프는 표본"이 세션·순간에
  따라 표본 크기가 크게 흔들린다는 뜻).
- 5개 봉 중 신호: `end` 가설 채택 2, `start` 가설 채택 1, 무승부(둘 다 오차 동일) 2.
  **다수결이지만 근거가 약하다** — 표본 부족 때문에 신뢰하기 어렵다.
- 결론을 소형주(저유동성, 50건이 여러 분을 덮음)로 재확인하려 했으나 §3의 가격 정밀도 문제로
  중단했다(에스컬레이션 진행 중 — 코디네이터 지시 대기).

### 2-2. 재확인 필요

이 항목은 **미완**이다. 저유동성 소형주(BTAI/CRKN 등)로 재시도가 필요하나, §3 이슈 때문에
`get_candles`가 그 종목들에서 SchemaMismatch로 실패한다. §3 해결(또는 회피 방법 확정) 후 재시도한다.

## 3. ⚠️ 설계 전제 위반 발견 — 계약 C-2 마이크로달러(1e-6) 정밀도가 CRKN(리버스 스플릿 종목)에서 깨짐 — `확인됨` (원인 확정), 계약 개정 A4 코디네이터 진행 중

A-3를 소형주로 재확인하려다 발견했다(원래 BTAI로 오인·보고했으나 **정정: 실제 종목은 CRKN**).
`client.get_candles("CRKN", "1m", count=6)` 호출이 다음 예외로 실패했다:

```
tossmon.api.errors.SchemaMismatch: candles.openPrice: precision finer than 1e-6: '0.10461614'
```

### 3-1. 원인 진단 (코디네이터 지시 P1~P3, 총 9콜)

**P1 — adjusted 가설 검증(확정)**: 문제의 CRKN 봉(`2025-03-05T08:00:00+09:00`)을
`adjusted=true`/`false` 로 각각 조회.

| adjusted | openPrice | 소수 자릿수 |
|---|---|---|
| true | `0.10461614` | 8 |
| false | `1.9889` | 4 (깨끗함) |

비율 `1.9889 / 0.10461614 ≈ 19.0114`(정수에 가까움) — **가설 확정**: `adjusted=true`(수정주가)가
과거 리버스 스플릿 비율(≈1:19, 배당 등 추가 보정이 섞여 있을 수 있어 정확히 19는 아님)을 곱해
파생값을 만들고, 이 나눗셈이 유한소수로 안 떨어지면서 임의 자릿수가 생긴다. `adjusted=false`
(원가)는 항상 깨끗하다.

**P2 — 엔드포인트 범위**: CRKN 외 `/trades`, `/orderbook`, `/prices`, `/candles(1d)` 및
BTAI·SNTI·DFNS 의 `/candles`(1m)는 전부 소수 4자리 이하로 정상이었다. **지금까지 관측 범위에서는
문제가 `/candles`(1m) 의 `adjusted=true` 경로, 그중에서도 과거 리버스 스플릿을 겪은 종목에
한정된다** (BTAI/SNTI/DFNS는 스플릿 이력이 없어 재현되지 않음).

**P3 — 종목 범위**: 소형주 4종 `/prices` 배치 1콜 — BTAI `0.7803`(4자리), SNTI `0.347`(3자리),
CRKN `0.0012`(4자리), DFNS `96.22`(2자리). 전부 정상.

### 3-2. 파급 범위와 설계 함의

- 계약 C-5 정책상 `SchemaMismatch`는 재시도 금지 + **해당 심볼 스킵**이다. 리버스 스플릿을 겪은
  저가 소형주는 정확히 이 프로젝트의 표적 종목군(docs/03 §1, 리버스 스플릿 이력 자체가 스윗스팟
  태그 중 하나 — docs/03 §1 Tier 0 보강 태그)과 겹친다 — **하필 노리는 종목군에서 과거 구간
  백필이 조용히 실패할 위험**이 실재한다.
- 범위는 "저가 종목 전반"이 아니라 **"adjusted=true + 과거에 스플릿을 겪은 종목의 스플릿 이전
  구간"으로 한정**되는 것으로 관측됐다(추측 아님 — P2 근거).
- 코디네이터 결정(권한 밖이라 자체 판단하지 않음): 단위는 마이크로달러 유지, 초과 정밀도는
  예외가 아니라 **반올림 처리**로 계약 개정(A4) 진행 중(W1이 CRKN 정정본 기준으로 구현·픽스처
  작성 중). 나노달러 전환은 가격×수량 누적의 int64 오버플로 위험(W3 VWAP 사례)과 sub-penny
  규정(Rule 612, $1 미만 최소호가 $0.0001) 대비 과도한 정밀도라 기각됐다.
- **계약 A5 신설(main 55c7d15, 코디네이터)**: 이 P1 결과가 더 근본적인 문제를 드러냈다 —
  수정주가(adjusted=true)는 **그 시점의 명목 가격을 지운다**. CRKN은 2025-03-05에 실제로는
  $1.99에 거래됐는데 수정주가로 보면 $0.10 동전주로 보인다. 이 프로젝트의 논지가 "동전주
  가격대에서 벌어지는 현상"인데, 수정주가로 과거를 보면 **당시엔 동전주가 아니었던 종목을
  동전주로 오분류**한다. sub-penny 호가·LULD 밴드($0.75/$3 경계) 등 미국 제도가 전부 명목
  가격 기준이라 미시구조 해석 전체가 틀어진다. **결정: 1분봉은 `adjusted=false`(원주가),
  일봉은 `adjusted=true`(수정주가)를 쓴다.** 분할은 장중에 일어나지 않으므로 일중 상대 변화
  (수익률·RVOL·VWAP 괴리)는 원주가로도 완전히 동일해 잃는 것이 없고, 다일 비교(베이스라인)만
  일봉(수정)으로 계산한다.
  **✅ 작업 B(야간 수집) 은 A5 적용 후(main `263a6ee`) 수집이다.** W4가 A5를 22:30 정규장
  개장 전에 `tossmon/collector/loops.py`에 반영·머지했고(`tier2_symbol_once`/`_backfill_1m`은
  `adjusted=False`, `_refresh_baseline`(일봉)은 `adjusted=True`를 명시적으로 호출 — 기본값을
  바꾸지 않고 호출부에서 명시하는 것이 계약이라는 코멘트가 코드에 남아 있다), 이 워커도 수집
  시작 전에 `git rebase main`으로 반영을 확인했다. 즉 §5의 1분봉은 원주가, 일봉 베이스라인은
  수정주가로 수집된 데이터다.

### 3-2b. A4 머지 후 검증 — 일봉(adjusted=true) 백필에서 `open_u`(등) 0u 뭉개짐 여부 — `부분확인`

코디네이터 요청(A4 머지 후, main `53578fb`): 극단적 리버스 스플릿이 누적된 종목의 아주 오래된
일봉은 수정주가가 1e-6 USD 미만으로 내려가 반올림(`ROUND_HALF_EVEN`)으로 `0u`가 될 수 있다는
우려 확인.

`main`을 rebase해 A4를 반영한 뒤, CRKN·BTAI·SNTI 세 종목의 **일봉(adjusted=true) 전체 이력**을
`nextBefore`로 끝까지 페이지네이션하며 `open_u/high_u/low_u/close_u` 전부를 검사했다(19콜).

| 종목 | 페이지 | 총 봉수 | 가장 오래된 봉 | 0u 뭉개짐 |
|---|---:|---:|---|---|
| CRKN | 1 | 41 | 2025-01-02 | 없음 |
| BTAI | 11 | 2,100 | 2018-03-08 | 없음 |
| SNTI | 7 | 1,294 | 2021-05-26 | 없음 |

- **A4는 "이론적 안전장치"가 아니라 실제 라이브 데이터에서 작동 중이다** — `precision_stats()`:
  `rounded=13/17179`, `max_digits=8`(최근 예 `0.28983126`). 즉 **13건이 실제로 발생했다.**
  A4 이전(예외 + 심볼 스킵) 코드였다면 이 13건은 전부 조용한 스킵으로 이어졌을 것이다 — "발생
  가능성이 있다"가 아니라 "이 리허설 세션에서만도 13번 발생했고, 전부 정상 처리됐다"로 기록한다.
  이 13건 중 `0`으로 내려간 사례는 없었다.
- **한계**: 3종목 표본이다. "관측 안 됨"이지 "발생 불가능함이 증명됨"은 아니다 — 더 극단적으로
  누적 리버스 스플릿을 겪은 종목(수차례 반복 스플릿)에서는 이론상 여전히 가능하다. 백필 실행 시
  `precision_stats()`를 주기적으로 점검하고, `rounded` 대비 `0`이 되는 사례가 실제 나타나면
  (`Store.upsert_candles_1d`에 들어가는 행에서 `open_u==0` 등을 직접 조회) 그 시점에 다시 보고할
  가치가 있다.
- **백필 계획 함의(신규)**: CRKN의 일봉 이력이 **2025-01부터 41봉뿐**이다(§3-2b 표) — 유니버스
  안에 **일봉 이력 자체가 짧아 20일 베이스라인(`compute_daily_baseline`)조차 못 만드는 종목**이
  섞여 있다는 뜻이다. 백필 계획(docs/03 §1-A)이나 유니버스 필터(docs/03 §1 Tier 0)에 "최소
  일봉 이력 길이" 조건이 필요한지는 코디네이터 판단 대상으로 남긴다(자체 판단 안 함).

### 3-3. 보너스 발견 (이번 이슈와 무관, 참고용) — CRKN 1분봉 정지 17개월+

CRKN은 `before` 없이(최신) 조회해도 1분봉 마지막이 `2025-03-05`다 — **17개월 넘게 1분봉
프린트가 없다**. `/prices.lastPrice` 는 `0.0012`로 응답은 오지만(A2 §3: 체결 없어도 lastPrice는
옴), 실질적으로 시간 단위가 아니라 **개월 단위**의 `no_print` 사례다. A2의 `first_print`/
`staleness_s` 설계가 다루려는 극단 사례의 실존 증거로 참고 가치가 있다(추가 조치·escalate는
불필요 — 설계 전제를 깨는 게 아니라 오히려 뒷받침하는 사례).

## 4. (A-1) 정규장/데이마켓 시세·호가·체결 거동 — 정규장 `확인됨`, 데이마켓 `미실행`

**일정 변경(코디네이터 지시, 2026-07-30 21:3x KST)**: 당초 22:30 개장 직후 실행 계획이었으나
취소했다. 이유: (a) `TokenManager`는 파일락 기반 단일 리스라 collector(작업 B)와

검증해야 사고를 미리 막는다"). 즉 설계는 의도대로 동작 중이며, 실사용률이 낮다고 정원(tier3_max)
을 늘리는 것은 **위험한 결론**이다 — tier3가 실제로 20개를 채우는 세션(더 활발한 밤)이 오면
그때 6.42 산식이 그대로 적용되기 때문이다.

## 16. 계획 정비와 진짜 사고를 구분 (2026-08-03 10:4x) — `적용됨`

### 16-1. 문제: 아침 점검 규칙이 무력화됐다

§15-2 의 **계획된** 재기동이 `ALERT_..._watch_process_dead.txt` 와
`ALERT_..._restarted_process_dead.txt` 두 건을 남겼다. 워치독 동작 자체는 정확했지만,
사용자에게 준 아침 규칙이 "`ALERT_*` 파일이 있으면 문제"였으므로 **의도된 정비가 사고와
똑같이 보였다**. 무인 운영에서 아침에 한 번 훑는 규칙이 흐려지면 그 규칙은 곧 안 쓰이게
되고, 진짜 사고를 놓치는 경로가 된다.

### 16-2. 계획 정비 창(window)

운영자가 의도적 정지·재기동 **전에** `data/ops_state/PLANNED` 마커를 만든다:

```
reason=rebase onto main, picking up the W4 blindspot fix
until=2026-08-03 10:45:00      # 생략 가능 — 없으면 파일 mtime + 30분
```

마커가 살아 있는 동안 워치독이 내는 경보는 `ALERT_` 대신 **`PLANNED_` 접두어**로 쓰이고,
본문 맨 위에 `PLANNED MAINTENANCE - this was expected, not an outage.` + 사유가 붙는다.
**`STOP` 파일에 의한 스탠드다운은 마커가 없어도 항상 `PLANNED_`** 다 — STOP 은 정의상
운영자 행위이기 때문이다.

**두 가지 안전 속성을 의도적으로 넣었다**:

1. **자동 만료·자동 삭제**: 만료된 마커는 무시하는 데 그치지 않고 워치독이 **지운다**.
   누가 마커를 지우는 걸 잊어도 5일 내내 경보가 죽는 일이 생기면 안 된다 — 이 방어층의
   존재 이유 자체를 마커 하나가 무력화할 수 있는 구조를 남기지 않는다.
2. **라벨만 바뀌고 복구는 그대로**: 계획 창 안에서도 프로세스 사망 감지·자동 재기동·재기동
   예산은 **전부 평소대로 동작**한다. 조용해지는 것은 파일 이름뿐이다.

**정직한 한계**: 계획 창 안에서 진짜 사고가 나면 그것도 `PLANNED_` 로 기록된다(위양성이
아니라 위음성). 그래서 창을 짧게(기본 30분) 잡고 본문에 원인 상세를 그대로 남긴다 —
사람이 열면 무슨 일이 있었는지는 전부 보인다. 창을 길게 잡는 운용은 권하지 않는다.

### 16-3. 검증 6/6 PASS + 소급 정리

마커 없음→사고는 그대로 `ALERT_`(회귀 방지) / 마커 활성→같은 사건이 `PLANNED_`+헤더 /
**계획 창에서도 자동 재기동은 실행됨** / 만료 마커→무시·자동 삭제·경보 복귀 / `until=`
명시(미래=활성, 과거=만료) / STOP 스탠드다운은 마커 없이도 `PLANNED_`.

오늘 아침 두 파일은 **소급 재분류**했다(`PLANNED_20260803_102556_watch_process_dead.txt`,
`PLANNED_20260803_102623_restarted_process_dead.txt` — 원문은 그대로 두고 헤더만 덧붙임).
따라서 지금 `data/` 에 `ALERT_*` 는 0건이고, **"ALERT 0건 = 무사"** 규칙이 다시 성립한다.
`daily_health` 요약도 두 종류를 나눠 센다(`ALERT files (24h, 진짜 문제)` /
`PLANNED files (24h, 계획된 정비)`).

**앞으로의 재기동 절차**(§15-2 를 이렇게 갱신): ① `PLANNED` 마커 작성(사유 포함) →
② `STOP` 생성 → 종료 확인 → ③ `STOP` 제거 → ④ 도구 호출을 비우고 워치독 사이클이 재기동
→ ⑤ 검증 후 `PLANNED` 마커 삭제(안 지워도 30분 뒤 자동 만료).

## 17. tier2 호가 활성화 (2026-08-03 11:21, 공백 9초) — `수집 중`

§15-6 에서 에스컬레이션한 tier2 호가가 W4 구현(main `4e6e24b`, `run_tier2_orderbook`)으로
들어와, W5 가 라이브 설정에 주기를 넣고 재기동해 **실제 수집을 개시**했다.

### 17-1. 설정값 600초의 근거

라이브 `config/config.yaml` 의 `polling:` 아래에 `tier2_orderbook_s: 600` 을 넣었다.
**이 파일은 gitignore 라 커밋 대상이 아니다** — W4 가 코드는 커밋했어도 라이브 값은 넣을
수 없었던 이유이고, 그래서 운영자(W5)가 넣어야 했다. 600 인 이유는 예산이다: 루프가
`sleep(period / len(tier2))` 로 도는 라운드로빈이라 **총 호출률은 심볼 수와 무관하게
1/period × len 이 아니라 len/period** 다 — tier2 가 상한(300종목)까지 차도
300/600 = 0.500 req/s 로 MARKET_DATA 여유 0.572 req/s 안에 들어온다. 300초로 잡으면
1.0 req/s 라 초과한다. 기동 시점 실제 tier2 는 71종목이라 0.118 req/s 로 훨씬 여유롭다.

**목적을 생각하면 성겨도 된다**: 필요한 것은 승격 *전* 스프레드 궤적이지 체결 순간의
마이크로 구조가 아니다(그건 tier3 의 16초 폴링이 이미 본다). 오히려 tier2 를 조밀하게
보면 tier3 예산을 잠식해 본론이 상한다.

### 17-2. 재기동 — 공백 9초

§16 마커 절차의 **첫 실전 적용**: ① `PLANNED` 마커(사유 기록) → ② `STOP` 11:21:10 →
③ 11:21:13 프로세스 0 확인 후 `STOP` 즉시 제거 → ④ `schtasks /Run tossmon-watchdog` 한 번
호출하고 **즉시 도구 호출 종료** → ⑤ 11:21:15 워치독이 `both_dead` 판정·재기동,

**수집 공백 11:21:13~11:21:22 = 9초** (§15-2 의 61초에서 개선). 정기 사이클을 기다리지 않고
워치독을 직접 한 번 깨우되, 프로세스 출생은 호출이 끝난 뒤에 일어나게 한 것이 차이다 —
§11-2 의 0xC000013A 회피 조건(에이전트 호출 공백)은 그대로 지킨다. 재기동 실패해도 다음

**마커 효과 확인**: 이번 재기동이 만든 경보 2건이 전부 `PLANNED_*` 로 기록됐고

`PLANNED_20260803_112144_restarted_process_dead.txt`) **`ALERT_*` 는 여전히 0건**이다.

- **`tier2_orderbook_snaps`** — 개장 세션에서 3주기(약 15분) 평평하면 WARN.
  이 실패 모드는 **오류를 안 남긴다**(설정이 0이거나 tier2 멤버가 없거나 루프가 멎어도
  조용하다). 오늘 코디네이터가 "30분간 3종목 255건, 여전히 tier3 뿐"으로 발견한 것이

- **`tier2_orderbook_skipped`** — 증가는 INFO. tier2 호가는 예산 압박·429 쿨다운에서
  **가장 먼저 희생되도록 설계**된 항목이라 사고가 아니다. 낮은 수집량의 *설명*으로 읽어야

요약줄에 `t2book=` 을 추가했다. **검증 5/5 PASS**(샌드박스): 평평 3주기→WARN / 증가 중→
무발화 / closed 세션 평평→무발화 / skipped 증가→INFO·재기동 안 함 / **구 수집기(카운터
부재)에서 오탐 0**. 마지막 항목은 처음에 FAIL 이 났는데, 원인은 코드가 아니라 픽스처가
동일 텔레메트리 줄을 반복한 것이었다 — 그건 진짜 동결 신호라 워치독이 옳게 잡은 것이고,
줄을 실제로 전진시키자 통과했다.

## 18. 디스크 회수 규칙 — 에이전트 스크래치 DB 사본 (2026-08-03 14:3x) — `적용됨`

### 18-1. 사고: 경보는 세 번 울렸는데 회수는 0MB

여유 디스크가 10.9GB → **5.06GB** 로 급감했고 워치독이 `disk_warn`(6.79GB)·`disk_reclaim`
(6GB 미만)을 냈지만 **회수량이 0MB** 였다. 원인은 W3 가 분석할 때마다 수집 DB(약 500MB)를
스크래치패드로 통째 복사하면서 **매번 새 번호를 붙인 것**이다 — `live_snapshot.db`,
`live2.db` … `live8.db` **8개 3.9GB**. 락 경합 회피를 위한 복사 자체는 옳은 판단이었고
(코디네이터 지시), 문제는 **누적**이었다.

**왜 내 회수 규칙이 하나도 못 잡았나**: 규칙이 "24시간 이상 손대지 않은 파일"만 지웠는데
이 사본들은 **전부 당일 생성**이었다. 나이 기준은 "잊힌 쓰레기"를 겨냥한 것이라, "오늘
만들어져 오늘 쌓이는" 패턴에는 원리상 무력하다. 결국 사람이 수동으로 3.4GB 를 지웠다.

### 18-2. 나이가 아니라 "세대"로 판정한다

새 범주를 넣었다 — **에이전트 스크래치 DB 사본**:
`%TEMP%\claude\**\scratchpad\*.db` 중 100MB 이상을 **스크래치패드 디렉터리 단위로 묶어**,
사본이 2개 이상이면 **가장 최근 1개만 남기고 나머지를 나이와 무관하게 회수**한다.

보존 조건을 세 겹으로 뒀다 — 남의 작업을 지우는 것이 디스크가 차는 것보다 나쁘기 때문이다:

1. **최신 1개는 항상 보존** — 지금 분석 중일 수 있다.
2. **열려 있는 파일은 절대 삭제 안 함** — `FileShare.None` 으로 열어보고 실패하면 사용
   중으로 간주해 건너뛴다(타임스탬프 추정보다 확실하다). 읽을 수 없는 어떤 이유든 사용
   중으로 처리한다 — 애매하면 지우지 않는 쪽.
3. **사본이 1개뿐인 스크래치패드는 손대지 않음** — 그건 누군가의 작업 세트다.
4. 100MB 미만은 제외(소소한 파일까지 건드릴 이유가 없다). SQLite `-wal`/`-shm`
   사이드카는 본체와 함께 지운다.

기존 "24시간 이상" 규칙에도 **사용 중 검사를 추가**했다 — 재사용 규율이 지켜져 사본이
하루 넘게 유지되는 경우, 그게 곧 활성 파일일 수 있기 때문이다.

이 보강은 **이중 방어**다. W3 에게는 별도로 "사본을 재사용하라"는 규율이 전달되지만,
규율이 안 지켜져도 디스크가 터지지 않게 하는 것이 워치독의 몫이다.

### 18-3. "0MB 회수"로 끝나지 않게 — 경보에 증거를 싣는다

이번 사고에서 사람이 수동 조사를 해야 했던 진짜 이유는 경보가 **"0MB 회수"만 말하고
어디가 찼는지는 말하지 않은 것**이다. 그래서:

- 회수 로그에 **무엇을 몇 MB** 지웠는지 항목별로 남긴다. 아무것도 못 지웠으면
  `reclaim: nothing eligible - freed 0MB` 를 명시적으로 남긴다(침묵과 구분).
- 경보 본문에 **회수 항목 목록**과 **현재 최대 소비처 상위 5개**를 항상 싣는다.
  회수가 0MB 면 조사 임계(8GB) 아래가 아니어도 **강제로 조사를 돌려** 목록을 채운다.
- 상위 소비처 조사에 **스크래치 DB 더미를 별도 항목으로** 표시한다
  (`[N scratch DB copies - reclaimable except newest]`) — 디렉터리 총량만 보면 사본이
  8개 쌓인 상황이 눈에 안 들어온다.

### 18-4. INFO 기록은 `ALERT_` 가 아니라 `NOTE_` (§16 규칙 보정)

작업 중 같은 계열의 결함을 하나 더 발견했다. `tier2_orderbook_skipped`(예산 양보 —
**설계된 동작**)가 INFO 인데도 `ALERT_` 로 쌓여 있었다. §16 에서 세운 "아침에 `ALERT_` 가
있으면 문제"라는 규칙을 다시 흐리는 것이라, **INFO 등급은 `NOTE_` 접두어**로 분리했다
(계획 창이면 `PLANNED_` 가 우선). 기존 파일 1건은 소급 재분류했다.

이제 세 갈래다: **`ALERT_` = 조치 필요(WARN/CRIT)**, `PLANNED_` = 계획된 정비,
`NOTE_` = 설계대로 동작한 기록. `daily_health` 요약도 3분류로 센다. 현재
ALERT 2건(둘 다 오늘 진짜 디스크 사고), PLANNED 4건, NOTE 1건.

### 18-5. 검증 9/9 PASS

가짜 `%TEMP%` 트리로 라이브 스크래치패드·수집기와 완전히 격리해 돌렸다:
최신 사본 보존 / 이전 세대 회수(나이 무관) / **열어둔 파일은 보존하고 SKIP 로그** /
사본 1개뿐인 스크래치패드 보존 / 100MB 미만 제외 / `-wal` 사이드카 동반 삭제 /
항목별 MB 로그 / 경보에 회수 목록+상위5 포함 / **회수 0MB 경로에서 강제 조사·상위5·
소비처 이름이 경보에 실림**(사고 재현 시나리오).

검증에 쓴 더미 사본 945MB 는 즉시 정리했다 — 내가 고치려는 문제를 내가 만들어 두는 것은
말이 안 된다(free 7.42GB → 8.35GB).

## 19. 워치독이 눈이 멀었고, 그 사실을 아무에게도 알리지 않았다 (2026-08-03 23:2x~23:50) — `해결됨`

### 19-1. 증상과 원인 — 로그 양이 이길 수 있는 창은 창이 아니다

23:25:54 부터 25분간 워치독이 매 주기 이렇게 찍었다:
`sup=1 col=1 session=unknown age_min=-1 problems=no_telemetry`.
**수집은 완전히 정상이었다**(랭킹 5초 전, 체결 4초 전, 최근 5분 9,200행) 그리고

눈이 먼 것은 워치독이다.

원인은 `Get-Content -Tail 400` 이라는 **줄 수 기반 창**이었다. 텔레메트리는 5분마다 1줄인데
티어 승격 로그는 분당 300줄까지 나온다 — 실측으로 최근 1000줄이 **3.2분**밖에 안 걸치고
그 안에 텔레메트리는 1줄, **최근 400줄에는 0줄**이었다. 즉 티어 활동이 조금만 활발해지면
**구조적으로 못 찾는다**. 평소에 통했던 것은 운이었다.

### 19-2. 진짜 결함 — 자기가 눈멀었음을 알면서 침묵했다

코드는 `problems=no_telemetry` 를 **로그에 적었지만 경보 파일을 만들지 않았다**.
`data/` 에 disk·schema 경보는 있는데 `no_telemetry` 경보만 없었다. 이 프로젝트에서
**다섯 번째 "성공을 반환하는 조용한 실패"** 다.

왜 이것이 심각한가: 워치독이 못 읽는 동안 **카운터 정체 탐지가 죽는다**. 그건 §11-1
(api_errors=0 인 채 API 전면 사망)을 잡아낸 **유일한 조기 신호**다. 즉 실명 상태에서는
수집기가 진짜로 죽어도 워치독이 못 잡는다. 사용자 요구가 "**내 개입 없이** 빠르게 되살릴 수
있게" 인데, 침묵하는 실명은 그 요구를 정면으로 배신한다.

### 19-3. 수정 — 1차 소스를 상태 파일로

**`data/collector_state.json` 을 1차 소스로 삼는다.** 수집기가 매 루프 다시 쓰는 20KB 고정
크기 JSON이라 **로그 양에 밀려날 수 없다.** 필요한 것이 전부 들어 있다: `session`,
`saved_ms`(신선도), `counters`(41종), `last_ranking_snap_ms`, `tiers`, `watchlist`.
텔레메트리 라인이 계산해서 보여주던 값은 여기서 유도한다 — `ranking_snap_age_s` 는
`last_ranking_snap_ms` 로, `fetch_success_pct` 는 `prices_seen`/`prices_missing` 으로,
`tier2_orderbook_skipped` 는 `_rate`+`_429` 합으로. **파일에 없는 카운터는 0** 이다(수집기가
증가한 키만 저장한다) — W4 계약 키들은 명시적으로 0 을 채워 넣어 "미지원"과 구분한다.

**폴백은 시간 기준 로그 스캔**이다. 줄 수가 아니라 "최근 N분을 실제로 덮을 때까지" tail 을
4배씩 늘리고 상한(20,000줄)에서 멈춘다. 상태 파일이 없거나 깨졌거나 오래됐을 때만 쓴다.
요약줄에 `src=state|log|none` 을 넣어 **어느 소스로 읽었는지**가 항상 보이게 했다.

### 19-4. 실명은 CRIT 경보다 — 이유까지 적는다

`no_telemetry` 를 CRIT `ALERT_` 로 승격했다(실명은 PLANNED 도 NOTE 도 아니다). 본문에
**왜 못 읽었는지**를 소스별로 적는다 — 상태 파일이 없는지/파싱 실패인지/오래됐는지,
로그가 없는지/시간 창 안에 텔레메트리가 없는지(로그 크기·최종 수정 시각 포함). 오늘 사람이
손으로 판정해야 했던 것이 정확히 이 정보다.

**실명으로는 자동 재기동하지 않는다**. 오늘처럼 수집기가 멀쩡한데 못 읽는 경우가 실재하고,
읽기 실패로 재기동하면 **막으려던 장애를 스스로 만든다**. 대신 경보에 "지금 카운터 정체
탐지가 꺼져 있다"고 명시해 사람이 판단하게 한다.

### 19-5. 빈 경보 파일 — 경보 경로 자체의 조용한 실패

지적받은 `ALERT_20260803_232058_schema_mismatch.txt` 는 **디스크상 232바이트로 비어 있지
않았다**(UTF-8 BOM 으로 시작). 0바이트로 보인 경위는 재현하지 못했으므로 단정하지 않는다.
다만 **경보 경로에 조용한 실패가 있으면 그게 최악**이라 방어를 넣었다: 본문이 비면 자리표시
문구를 넣고 로그에 결함으로 남기고, 쓴 뒤 **실제 파일 크기를 확인**해 0이면 1회 재시도하고
그래도 0이면 **경보 본문을 워치독 로그에 통째로 남긴다**(내용 유실 방지). 덧붙여 경보
파일을 **BOM 없이** 쓰도록 바꿨다 — 사람이 읽는 평문 파일이고 BOM 은 일부 도구에서 첫 줄을
깨져 보이게 한다.

## 20. 워치독이 정상을 사고로 오인해 멀쩡한 수집기를 재시작했다 (2026-08-04 08:55) — `해결됨`

### 20-1. 사고 — 어제의 수정이 만든 새 실명 지점

§19 에서 1차 소스를 `collector_state.json` 으로 바꿨다. 그 파일은 **수집기가 일을 할 때만
다시 쓰인다**. 그래서 세션이 닫히는 순간 **마지막 열린 세션 값인 채로 얼어붙는다.**

```
08:49:44  collector_state.json 마지막 저장 (session="after")
08:50:09  collector.log: "session after -> closed"  <- 진짜 세션은 여기서 바뀌었다
08:55:10  collector.log 텔레메트리: session=closed, ranking_snap_age_s=311
08:55:54  watchdog: session=after (6분 묵은 상태 파일) -> openSession=true
          ranking_snap_age 382s > 300s -> CRIT "랭킹 루프가 조용히 멈췄다 ...
          이 상태의 매 분이 영구 데이터 손실" -> 재시작
08:56:14  수집기 재기동
```

**아무 문제도 없었다.** 08:50~09:00 KST 는 토스 캘린더에 세션이 배정되지 않은 구간이라
랭킹이 쉬는 게 설계대로다(스케줄러 계약 C-8). 이 구간은 **매일 있다.** 즉 이 재시작은
매일 한 번씩 일어나게 되어 있었다. 재시작은 이 프로젝트 데이터 손실 원인 1위다.

결함은 두 겹이었다.

1. **낡은 값을 1차 소스로 믿었다.** 신선도 기준이 15분이라 6분 된 파일은 통과했다.
2. **`ranking_snap_age_s` 를 현재 시각 기준으로 계산했다.** 얼어붙은
   `last_ranking_snap_ms` 와 지금의 차이라서, 수집기가 완벽히 정상이어도 **기다리기만 하면
   반드시 임계를 넘는다.** 경보가 아니라 타이머였다.

### 20-2. 수정 — 관측 시점 기준으로 재정의

**(a) 나이는 관측 시점 기준으로 잰다.** `ranking_snap_age_s = saved_ms -
last_ranking_snap_ms`. "우리가 마지막으로 볼 수 있었던 그 순간에 랭킹 루프가 얼마나
뒤처져 있었나"라는, 경보가 원래 가정하던 뜻으로 돌아간다. 사고 시점 값은 382 가 아니라
**12** 이고, 이는 수집기 자신의 텔레메트리(`ranking_snap_age_s=10`)와 일치한다.
"그 관측이 얼마나 묵었나"는 별개 사실이므로 `age_min` 으로 따로 보고한다.

**(b) 낡은 관측의 `session` 은 안 믿는다.** 새 임계 `StateTrustS`(300초, = 랭킹 임계).
이보다 오래된 관측의 세션은 `unknown` 으로 강등되고, **`unknown` 은 열린 세션이 아니다**
(예전엔 `-ne "closed"` 뿐이라 unknown 이 모든 판정을 켰다 — 못 보는 것은 행동할 이유가
아니라 삼갈 이유다).

**(c) 낡았으면 로그로 폴백한다.** 수집기는 **닫힌 세션에도 5분마다 텔레메트리를 남긴다.**
상태 파일이 멈추는 바로 그때 로그는 계속 흐른다 — 그래서 실제 세션(`closed`)을 갖고 있다.

**(d) 신선한데 이미 틀린 경우까지 막는다.** 08:50:55 의 상태 파일은 **71초밖에 안 됐는데**
세션은 이미 틀렸다(08:50:09 에 이미 닫혔다). 파일은 신선하면서 동시에 낡을 수 있다.
그래서 재시작 직전에 **자기보다 새로운 텔레메트리 줄**이 `closed` 라고 말하면 판정을
취소한다. 오래된 로그 줄은 아무것도 못 뒤집는다 — **더 새로운 관측만** 이길 수 있다.

**(e) 유예 두 가지.** 큰 `ranking_snap_age_s` 가 *정지*의 증거가 되려면 루프가 스냅샷을
찍을 시간이 있었어야 한다. ① 세션이 열린 지 300초 미만(09:00 경계 — 첫 랭킹 폴 전이면
직전 세션 값을 물려받아 크다) ② 수집기가 뜬 지 300초 미만(재기동은 상태 파일에서
`last_ranking_snap_ms` 를 **이어받는다** — 여기서 판정하면 재시작 루프가 된다).
유예 시계는 **세션 이름이 바뀔 때마다** 다시 시작한다. `closed` 를 볼 때만 리셋하면,
로그 폴백이 안 되는 날엔 `after -> (unknown) -> day` 로 전이를 아예 못 보고 넘어간다.

**(f) 억제는 침묵이 아니다.** 유예로 막은 판정은 `watchdog.log` 에
`ranking judgment SKIPPED` 로 남고 `NOTE_*_ranking_stall_suppressed` 파일이 생긴다
(ALERT 아님). 이 프로젝트에서 조용한 성공 반환은 여섯 번 사고를 냈다.

### 20-3. 아침에 30초 안에 판별할 수 있게

재시작 경보 본문이 한 줄이라 오늘 아침 사람이 한참을 썼다. 이제 모든 재시작 경보와
랭킹 경보에 **EVIDENCE 블록**이 붙는다 — 어느 소스로 읽었는지, 언제 관측했는지, 세션과
그 신뢰 여부, 세션이 열린 지 얼마인지, 수집기가 뜬 지 얼마인지, 얼어붙은 상태 파일이
뭐라고 주장했는지, 그리고 **독립 교차확인**(가장 새로운 `collector.log` 텔레메트리의
세션). 이어서 "이 재시작이 정당했나"를 읽는 법이 붙는다: 세션이 NOT TRUSTED 이거나
교차확인과 어긋나면 그 판정은 낡은 값 위에 선 것이고 **워치독 결함으로 보고할 일**이다.

`watchdog.log` 요약줄에도 `session=day(raw=after,stale=372s)` `open_for=` `col_up=` 이
들어간다 — 소스가 뭐라 했는지와 워치독이 무엇을 믿었는지가 늘 같이 보인다.

### 20-4. `schema_mismatch` CRIT 도 거짓이었다 — 근거보다 세게 단정하지 않는다

문구는 "**API 응답 형식이 바뀌었다. 재시작으로 안 고쳐진다. 오늘 데이터를 믿기 전에
엔드포인트 계약을 확인하라**" 였다. 실제로는 지금까지 오른 5건이 **전부**
`http-404 code=stock-not-found` — 상장폐지·거래정지 종목 하나를 조회한 것이다.
데이터를 의심할 이유가 전혀 없었다.

카운터 분리는 W4 몫이고 이미 들어왔다(main `4397130`, `symbol_not_found` 신설).
**경보 쪽은 이름이 아니라 근거로 판정한다** — 로그 최근 5,000줄에서 실제
`schema mismatch (skip)` 줄을 찾아 분류하고, 심각도를 근거에 맞춘다.

| 로그에서 본 것 | 등급 | 본문 |
|---|---|---|
| 전부 `http-404 code=stock-not-found` | INFO(NOTE) | 없는 종목이다. 형식 변경 아님, 데이터 정상 |
| 하나라도 다른 것이 있다 | CRIT | 진짜 형식 변경일 수 있다 (강한 문구 유지) |
| 해당 줄을 못 찾았다 | WARN | **모른다**고 적는다. 어느 쪽으로도 단정하지 않음 |

이 규칙은 구/신 수집기 양쪽에서 맞다: 옛 빌드는 404 를 `schema_mismatch` 로 세지만 로그
줄을 보면 정체가 드러나고, 새 빌드는 `symbol_not_found` 로 따로 세며 그쪽은 항상 NOTE 다.

### 20-5. 검증 — 가드를 직접 깨봤다

`ops/watchdog_selftest.ps1` 을 새로 넣었다. 진짜 `watchdog.ps1` 을 **자식 프로세스로**
샌드박스(`$env:TEMP`)에서 돌리고 `-DryRunRestart` 로 재시작을 의도만 남긴다.
가동 중 수집기는 건드리지 않는다.

```
powershell -NoProfile -ExecutionPolicy Bypass -File ops\watchdog_selftest.ps1
```

핵심은 **수정 전 코드로도 돌려봤다**는 것이다. "가드를 만들었다"가 실제로는 목록에 적힌
것만 검사한 사례가 이 프로젝트에 세 번 있었다.

| 케이스 | 수정 전 | 수정 후 |
|---|---|---|
| R1 정상 세션은 조용하다 | PASS | PASS |
| F1 08:55 사고 재현(언 상태 파일 + 로그는 closed) | **FAIL — 재시작함** | PASS |
| F2 상태 파일 얼고 로그 폴백도 불가 | **FAIL — 재시작함** | PASS |
| F3 09:00 세션이 막 열림 | **FAIL — 재시작함** | PASS |
| F4 수집기가 막 뜸(스냅 시각 물려받음) | **FAIL — 재시작함** | PASS |
| F5 상태 파일은 71초로 신선한데 세션이 이미 틀림 | **FAIL — 재시작함** | PASS |
| F6 `closed` 를 한 번도 못 본 채 after -> day | **FAIL — 재시작함** | PASS |
| **T1 진짜 랭킹 정지 -> 여전히 재시작한다** | PASS | **PASS** |
| **T2 양쪽 소스 전부 사망 -> log_stale 재시작** | PASS | **PASS** |

| S1 404 뿐인 schema_mismatch -> NOTE | **FAIL — CRIT 냄** | PASS |
| **S2 진짜 형식 변경 -> 여전히 CRIT** | PASS | **PASS** |

| S4 `symbol_not_found` -> NOTE | **FAIL — 아무 경보 없음** | PASS |

수정 전 13 PASS / 31 FAIL, 수정 후 **44 PASS / 0 FAIL**. T1·T2·T3·S2 가 양쪽에서 PASS 인
것이 중요하다 — 경보를 통째로 꺼서 통과시킨 게 아니라는 증거다.

F1 이 수정 전 코드에서 남긴 줄은 실제 사고 줄과 사실상 같다:
`session=after age_min=6.2 rank_age=385 -> RESTART` (실측 08:55:54 는 `rank_age=382`).

**라이브 확인**: 스케줄러가 도는 파일이 바로 이 파일이라 수정은 즉시 반영됐다.
14:25~14:45 다섯 주기 모두 정상 —
`session=day age_min=0.3 src=state open_for=300s col_up=3598s rank_age=1`,
새 경보 0건, 재시작 0건. 정규장 중이었고 **수집기는 무접촉**(STOP 없음, 프로세스 그대로).
pytest 1540 passed / 1 skipped (파이썬 코드는 건드리지 않았다).

한 가지 관측: 14:40 주기에 `open_for` 가 한 번 0 으로 떨어졌다. `session_name` 필드가
아직 상태 파일에 없어서 `"" != "day"` 로 읽혀 유예 시계가 리셋된 것이다 — **필드 도입
1회성**이고, 다음 주기(14:45)에 `open_for=300s` 로 정상 누적됐다. 워치독 상태 파일을
지우면 같은 일이 한 번 더 일어난다(한 주기 동안만 랭킹 정지 판정이 유예된다).

### 20-6. 남은 것 / 다음 사람이 알아야 할 것

- **`RankingSnapAgeCritS`(300초)는 세션 없는 구간(10분)보다 짧다.** 지금은 폴백·유예·교차
  확인 세 겹으로 막지만, 근본적으로는 **워치독이 토스 캘린더를 직접 모른다.** 수집기가
  세션 전이 때 상태 파일을 한 번 더 쓰게 하면(= `closed` 를 파일에 남기면) 이 전제 자체가
  사라진다. 그건 `tossmon/**` 이라 W5 소유가 아니다 — W4 에 제안한다.
- 유예 시계가 세션 이름 변경마다 리셋되므로 `pre/regular/after` 경계마다 랭킹 정지 탐지가
  **최대 1주기(5분) 늦다.** 매일 한 번의 거짓 재시작과 맞바꾼 값이다.
- `Get-CollectorUptimeS` 는 `Win32_Process.CreationDate` 를 읽는다. 못 읽으면 -1 이고
  **유예 없이** 예전과 똑같이 동작한다(안전한 쪽 실패가 아니라 예전 동작으로의 실패다).
