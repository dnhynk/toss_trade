## 1. 미수신이 폴 탓이 아니라는 근거

폴 주기가 셋 다 다른데 미수신율이 같다.

| 폴 주기 | 미수신율 | 출처 |
|---|---:|---|
| **1 초** | 33.3% | `docs/75` §4-1, 08-18 보존 JSON |
| **10 초** (웹) | 32.6% | 이 문서 |
| **12 초** (우리) | 34.0% | 이 문서 |

**1 초로 긁어도 3 분의 1 이 안 온다.** 폴 별칭(aliasing)이면 주기가 다를 때 값이 달라져야
한다. 안 달라진다. 따라서 결손은 **원천에서 생긴다.**

## 2. 폴을 빠르게 해도 사는 것이 거의 없다

`docs/75` §0 의 같은 자료에서 나이는 이렇다.

| 폴 주기 | 나이 p50 |
|---|---:|
| 1 초 | 16.795 s |
| 5 초 | 18.0 s |
| 12 초 | 18.1 s |

**12 배 빠르게 폴해서 1.3 초를 산다.** 나이는 폴 위상이 아니라 **원천이 내주는 시점**이
지배한다. `docs/58` **B. 속도** 갈래의 *"폴 주기 5 초 비용"* 은 이 표 위에서 다시 값을
매겨야 한다 — **1.3 초에 그 비용을 낼 것인가**가 실제 질문이다.

## 3. `docs/75` §4-1 의 두 칸 추론은 기각됐다

`docs/75` 는 고유 `rankedAt` **13 개**에서 `:29`·`:59` 가 0 인 것을 보고 *"우리 응답
경로가 여섯 칸 중 네 칸만 낸다"* 고 읽었다. **재현되지 않는다.**

2026-08-27 15:11~22:00 의 고유 개정본 **1,620 개**에서 초 자리는
`:09` 267 · `:19` 264 · `:29` 253 · `:39` 265 · `:49` 265 · `:59` 263 로 **균등**하다.
웹도 여섯 칸을 다 낸다. **고정 두 칸 결손은 표본 13 개의 착시였다.**

`docs/75` 의 **33% 라는 크기 자체는 살아 있다** — 위 §1 에서 세 주기 모두 재현됐다.
죽은 것은 *"어느 칸이 빠지는가"* 라는 그 문서의 설명뿐이다.

## 4. 재현 절차

```
# 웹 (오픈 API 를 부르지 않는다. 로그인하지 않는다. 새로고침을 강제하지 않는다)
<scratch>/g1a/.venv/Scripts/python.exe <scratch>/g1a/g1a_web_probe.py \
  --url "https://www.tossinvest.com/?market=us&live-chart=biggest_total_volume&duration=realtime&focusedProductCode=US20210719003" \
  --seconds 420 --recon --keep-re "overview/ranking" --out tvol_long.jsonl
<scratch>/g1a/.venv/Scripts/python.exe <scratch>/g1a/analyze.py tvol_long.jsonl TOSS_SECURITIES
```

응답 본문의 `result.basedAt` 이 서버 발행 시각이고 `products[].price.tossSecuritiesVolume`
이 우리 `rankings_snap.vol_qu` 와 같은 값이다. `priceType` 이 `SIMPLE` 인 응답은 다른
피드이므로 **반드시 걸러야 한다** — 안 거르면 초 자리에 `:51` 같은 값이 섞인다.

우리 쪽은 `rankings_snap` 에서 `ranking_type='TOSS_SECURITIES_TRADING_VOLUME'`,
`duration='realtime'`, `ranked_at_ms IS NOT NULL` 로 같은 창을 읽는다.
**2026-08-27 15:11 이전 행은 `ranked_at_ms` 가 NULL 이다**(`docs/77`).
