## 6-1. 무엇이 문제였나

2026-08-14 창이 §3-4.1 에 걸려 **무효**로 판정됐다 (공백 4 건: 62.7 / 65.3 / 71.6 /
74.1 초, 넷 다 개장 첫 30 분). 집행 기록은 `coordination/daily/2026-08-15.md`.

그 판정을 집행한 세션이 **같은 규칙을 기준선 10 세션에 그대로 적용해 봤고**
(`daily/2026-08-15.md` §5), 이것이 나왔다:

```
기준선 10 세션 중 5 개가 같은 규칙에 걸린다
  07-31  484초    08-07  254초    08-03·08-04  ~130초    08-05  75초
그리고 08-14 의 최대 74.1 초는 그중 가장 짧다
```

**§3-1 의 통과 문턱 25.9% 는 바로 그 다섯이 만든 값 위에 서 있다.** 규칙을 엄격히
적용하면 문턱 자체가 무효인 밤들에서 나온 셈이다.

**그리고 규칙이 더 큰 것을 놓친다**: 08-05 는 `tail = 3,929.5 초` — **창이 닫히기
65 분 전에 수집이 끝났다.** 창의 **16.8%** 를 못 봤는데 §3-4.1 은 *"창 안의 공백"* 만
보므로 **통과했고**, 그 세션의 22.9% 가 기준선 표에 그대로 들어가 있다.

> **즉 결함은 "60 초가 너무 작다" 가 아니라 자의 축이 틀렸다는 것이다.**
> 단일 최대 공백 하나로 판정하면 **6.5 시간 창에서 61 초 한 번**은 잡으면서
> **65 분 조기 종료**는 놓친다.

## 6-2. ★ 새 규칙 — **§3-4.1 을 이것으로 대체한다**

창 `[lo, hi]` = 13:30~20:00 UTC (`window_s` = **23,400 초**).
`S` = 그 창 안 `rankings_snap` 의 정렬된 distinct `snap_ms` (**전 `ranking_type` 합산** —
§3-4.1 의 모집단 정의를 그대로 승계한다).

```
head_s       = (S[0]  - lo) / 1000
tail_s       = (hi - S[-1]) / 1000
interior_s   = sum over consecutive pairs of  max(0, (S[i+1] - S[i])/1000 - 60)

unobserved_s    = head_s + tail_s + interior_s
unobserved_frac = unobserved_s / 23400

무효  <=>  unobserved_frac > 0.005        (0.5% = 117.0 초)
```

**설계 근거 셋**

1. **총량으로 판정한다.** 공백이 모집단과 분자를 동시에 깎는 정도는 *"가장 긴 공백"*
   이 아니라 *"못 본 시간의 총합"* 에 비례한다.
2. **60 초를 새로 정하지 않고 재활용했다.** 얼린 §3-4.1 의 60 초를 *"정상 간격의 상한"*
   으로만 쓰고(폴 주기는 `rk12s`), 판정은 총량이 한다. **새 숫자를 하나라도 덜 지어내려고**
   그렇게 했다.
3. **앞머리·꼬리는 전액 센다.** 60 초 면제를 거기에도 주는 변형을 검토했지만 **안 썼다** —
   사용자가 0.5% 를 고를 때 본 숫자가 전액 계산 기준(08-14 = 0.20%)이었고, 뒤에 식을
   바꾸면 **사용자가 판단한 근거와 다른 자가 된다.** 일관성보다 이쪽이 우선이다.
   (그 변형이면 08-14 는 0.144% 가 된다. 판정은 둘 다 같다.)

**문턱 0.5% 는 사용자가 골랐다** (선택지 0.5 / 1 / 2%). 대가도 함께 제시했다 —
더 엄격해서 기준선에서 살아남는 세션이 줄고 표본이 작아질 위험.

## 6-3. ★ 이 개정을 쓸 때 **내가 이미 알고 있던 것** — 숨기지 않는다

개정의 값어치는 *"결과보다 앞섰는가"* 다. 그런데 이 개정은 **08-14 의 공백을 이미 본 뒤에**
쓰였다. 그래서 무엇을 알고 썼는지를 적는다.

| 알고 있었다 | 값 | 새 규칙에서 |
|---|---|---|
| **08-14** (판정을 촉발한 밤) | 33.7 + 10.5 + 2.3 = **46.5 초 → 0.20%** | **통과했을 값이다** |
| 08-05 | 3,929.5 + 15.2 + 10.6 = **3,955 초 → 16.9%** | **무효** (옛 규칙은 통과시켰다) |

둘 다 `daily/2026-08-15.md` §5 의 공개된 표에서 계산된다. **즉 나는 새 규칙이 08-14 를
통과시킨다는 것을 알면서 이 규칙을 제안했다.** 사용자에게도 그렇게 제시했고 사용자가
그 위에서 골랐다.

**나머지 기준선 8 세션은 계산하지 않았다.** 규칙을 커밋하기 전에 계산하면
*"문턱이 어느 쪽으로 움직이는지 알고 규칙을 고르는 것"* 이 되기 때문이다.
**순서를 이렇게 지킨다**:

```
① 이 절을 커밋한다                      <- 지금. 대상 창이 열리기 2.6시간 전
② 그다음 기준선을 새 규칙으로 다시 판정하고 문턱을 다시 뽑는다
③ 오늘 밤(08-15 창)부터 그 자로 잰다
```

## 6-4. 적용 범위 — **앞으로만**

| | |
|---|---|
| **2026-08-14 창** | **무효로 유지한다.** 재판정하지 않는다 |
| **2026-08-15 창부터** | 새 규칙(§6-2)으로 판정한다 |
| 기준선 10 세션 | 새 규칙으로 **다시 판정**한다 (②). 그래야 자와 관측이 같은 자가 된다 |

**08-14 를 재판정하지 않는 이유**: 그 밤의 데이터는 이미 존재하고 그 공백을 이미 봤다.
새 자로 다시 재면 *"결과를 보고 자를 바꿔 다시 재기"* 가 된다. **하루를 벌 수 있지만
개정의 정당성을 잃는다.** 사용자 결정이다 (선택지 둘 중 *"앞으로만"*).
