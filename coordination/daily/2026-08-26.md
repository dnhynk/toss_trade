## 7. 워커 감독 체계를 복구했다 (오케스트레이션)

**새 `E` 설계를 fable max 워커에 붙이면서, 08-23 에 사라진 걸 확인했던 Run 을 다시 세웠다.**

핸들·복구 절차는 `COORDINATOR-STATE` §0 에 박았다. `ops/ops_config.yaml` 의
`orchestration_run_id` 도 새 Run 으로 고쳐 `ops/dispatch_sweep.py` 가 다시 훑는다.

### 7-1. ★ 실측 — **이미 도는 에이전트는 `--terminal` 로 못 묶는다**

먼저 터미널을 직접 띄우고(`terminal create --command "claude --model fable --effort max"`)
`worker-start --terminal <handle>` 로 묶으려 했더니 **`agent_readiness` 에서 60 초 뒤
`timeout`** 으로 죽었다 (`ctx_7a6e9707f78f`, 08:40:45 → 08:41:45). **에이전트가 생각
중이라 readiness 신호를 못 냈다.**

**정석은 Run·Task 를 먼저 만들고 `worker-start --agent claude --model fable --effort max`
로 띄우는 것이다.** 그 경로가 **수명주기 preamble 을 같이 넣어줘서** 워커가
`worker_done` 을 낼 수 있게 된다 — 직접 띄운 터미널에는 그게 없어서 애초에 감독이
성립하지 않았다.

`ORCA-OPERATIONS` §5 는 *"우리 워커는 이미 살아 있는 터미널이므로 `--terminal` 재사용이
맞다"* 고 적고 있는데, **그건 워커가 놀고 있을 때만 맞다.** §7-1 에 조건을 덧붙였다.

### 7-2. 모델은 두 번 확인했다

앞서 백그라운드 서브에이전트를 `model: fable` 로 띄우고 **실제 모델을 확인하지 않는
실수를 했다.** 인자를 넣은 것과 그게 먹은 것은 다르다. 이번엔 둘 다 봤다:

```
launch.effective : {"agent":"claude","model":"fable","effort":"max"}   <- 런타임 영수증
화면             : "thinking with max effort" / "bypass permissions on"
```

### 9-1. (가) 의 전제는 절반만 참이었다

| | |
|---|---|
| **사전 상태** | ✅ **된다.** 봉은 좌석이 사건 뒤에 와도 남는다 — **tier2 폴이 폴마다 최신 200 봉을 소급**한다. 앵커 429 중 봉 키 정의 **410 (95.6%)**, 수집 구멍 **0** |
| **위약** | ❌ **안 된다.** 위약의 **전방 경로가 여전히 테이프**라 위약 후보는 *그 종목이 그 세션에 좌석을 가진 초*뿐이고, 첫 진입엔 그런 초가 없다 |

```
정규장 첫 진입 79 건 -> 헤드라인 밴드 짝 12 (세션당 2.0), 밴드 다 풀어도 46

   -> 어느 층·어느 폭도 못 미친다
```

**앞 문서가 미리 박아 둔 눈금이 이번 자를 기각했다.** 사전등록이 설계대로 작동한 사례다.

> 인용 경고(워커): **"봉은 쓸모없다" 로 읽지 마라.** 봉은 사전 상태를 **만든다.**
> 못 만드는 건 위약의 **결과**이고, 그건 *테이프가 좌석의 함수*라는 사실이지 봉의 결함이 아니다.

### 9-2. ⚠ 정정 — **"첫 진입 142" 는 첫 진입이 아니었다**

`docs/68` §4-1·§5 가 142 건을 *첫 진입*이라 불렀는데 그것은 **좌석 시점의 층**이었다.
랭킹 이력으로 세면 **142 중 117 이 재진입**(쿨다운 600 초·좌석 2 석에 막혀 기다린 것)이고
진짜 정규장 첫 진입은 그 층에서 **25**, 429 전체에서 **79** 다.

`docs/68` §5 의 논리(*좌석이 사건 뒤에 온다*)는 그대로 참이다. **그 논리가 가리키는 사건이
142 가 아니라 79 였다.** W3 가 자기 전임자의 명명을 스스로 잡았고, **코디네이터도 그 142 를
사용자에게 그대로 전했다** — 같이 정정한다.
