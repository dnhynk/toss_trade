# W5 — 계측이 우리에게 거짓말하는 곳 네 군데 (2026-08-09 일일 코디네이터 실측)

오늘 아침 실행에서 **수집은 아무 문제가 없었다.** 문제는 전부 **계측 쪽**이었다.
네 건 다 같은 병이다: **창(window)이 잘못 정의돼 있거나, 실패가 조용하다.**

시장은 **월요일 22:30 KST 까지 닫혀 있다** — 지금이 계측 도구를 고칠 가장 싼 시간이다.
수집기는 건드리지 않는다(watchdog.ps1 은 5분마다 새로 실행되므로 재시작 불필요).

---

## 사실 (전부 오늘 실측, 재현 명령 포함)

### (1) 로그 패턴 경보의 창에 시간 상한이 없다

`ops/watchdog.ps1:1478` 이 `$tailText = (Get-LogTail 500)` 로 **줄 기준** 창을 잡고,
`:1481-1494` 의 **패턴 6개 전부**가 이 하나의 창을 공유한다
(`log_auth_failure`(CRIT) · `log_forbidden` · `log_rankings_store` · `log_rankings_clamp` ·
`log_precision_drift` · `log_tape_gap`).

실측 — 같은 500줄이 덮는 시간이 장 상태에 따라 20배 흔들린다:

| 시점 | 최근 500줄이 덮는 실제 시간 |
|---|---|
| 금 정규장 23:30 | 113분 |
| 금 정규장 01:00 | 77분 |
| 금 정규장 03:00 | 74분 |
| **일요일 09:33 (지금)** | **1,507분 = 25.1시간** |

> **코디네이터 정정**: 처음엔 *"바쁘면 500줄이 몇 분밖에 안 돼 진짜 경보를 놓친다"* 고
> 의심했으나 **실측으로 기각됐다** — `collector.log` 는 요청마다 찍지 않고 5분 텔레메트리
> 위주라 첨두에도 74분은 덮는다. **피해는 한 방향뿐이다: 죽은 사건이 무한 재발화한다.**

지금 벌어지고 있는 일:

```
원 사건 1건:  2026-08-08 08:46:12  ERROR  precision drift ... 표본 '5.70891193'
              (collector.log 227,207번째 줄 = 끝에서 331줄 -> 500줄 창 안)
결과:         ALERT_*_log_precision_drift 파일 25개
              20260808_085102 ~ 20260809_092100, 정확히 매시간
              (Raise-Alert ... 3600 = dedup TTL 1시간)
```

주말이라 로그가 5분에 한 줄만 늘어 **그 한 줄이 창 밖으로 못 나간다.**
월요일 개장 전까지 계속 쌓인다.

**경보 본문은 "언제"를 말하지 않는다** — `"Occurrences in the last 500 log lines: 1"`
뿐이라, 파일을 열어도 이게 25시간 전 사건인지 방금 난 사건인지 알 수 없다.

재현:
```bash
cd w5-ops
grep -n "precision drift" data/collector.log        # 227207번째 줄, 08-08 08:46:12
tail -500 data/collector.log | head -1 | cut -c1-20 # 창의 시작 시각
ls data/ALERT_*log_precision_drift* | wc -l         # 25
```

**원 사건 자체는 사고가 아니다** — 텔레메트리 기준 `precision_rounded=19 /
precision_parsed=1,783,017 = 0.001%`, `precision_max_digits=8`. $5 짜리 주식의
소수점 7~8자리 반올림이다. **고칠 것은 경보이지 파서가 아니다.**

### (2) 결손 감사가 **주말 창 전체를 사고로 보고**한다

일요일 아침 리포트(창 = 토 09:00 ~ 일 08:50)에는 미국장이 **아예 없다**.
그런데 `max_hole` 이 창 전체를 "설명되지 않은 공백"으로 찍는다:

| 리포트 | 요일 | max_hole | 랭킹 폴 |
|---|---|---|---|
| 20260808 | 토(금요일장 포함) | **4.2분** [inter_poll] | 16,416회 |
| 20260802 | **일** | **1430.0분** [whole_window] → `ALERT_` | 0회 |
| 20260809 | **일** | **1430.0분** [whole_window] → `ALERT_` | 0회 |

```
-> ALERT_ 1430.0분이 계획 창 **밖** — 설명되지 않은 공백
!! 설명되지 않은 가장자리 공백이 있다 — 기계가 잤거나 수집이 창 끝에서 죽었다.
```

**둘 다 거짓이다. 기계는 깨어 있었고 수집기도 살아 있었다** (오늘 `sup=1 col=1`,
`col_up=90,301s`, 재기동 0회). 볼 것이 없었을 뿐이다.

감사기는 `PLANNED_` 정비 창만 알고 **"장이 안 열린 시간"이라는 개념이 없다.**

> **이게 왜 중요한가**: `max_hole` 은 이 리포트에서 가장 중요한 한 줄이다 —
> 08-06 의 5시간 55분 정전을 옛 지표(`max_inter_poll` 1.3분) 대비 **227배** 차이로
> 잡아낸 바로 그 지표다(`COORDINATOR-STATE` §4.11 발견 1). 그게 주말마다
> 늑대를 외치면 **읽는 사람이 그 줄을 건너뛰게 훈련된다.**

미확인: **월요일 리포트(창 = 일 09:00 ~ 월 08:50)도 장이 없다.** 같은 증상일 것으로
보이나 08-03 리포트는 `max_hole` 도입 **전** 코드로 생성돼 확인이 안 된다.
**추측하지 말고 재봐라.**

### (3) 예약 작업이 죽어도 아무도 모른다

오늘 아침 리포트가 **결번됐다.** 기계는 켜져 있었다:

```
tossmon-dailyhealth   last=2026-08-09 08:52:01   result=3221225786   next=2026-08-10 08:52:00
                                                        = 0xC000013A = STATUS_CONTROL_C_EXIT
```

작업은 **실행됐고 콘솔 제어 이벤트로 죽었다.** `ExecutionTimeLimit=PT10M` 이므로
시간 초과(`0x41306`)가 아니고, `LogonType=Interactive` 라 콘솔에 붙어 돈다.
같은 서명이 `tossmon-collector-oneshot` 에도 남아 있다(08-04, `result=3221225786`).

> **무엇이 08:52 에 콘솔을 정리했는지는 증거가 없다.**
> Task Scheduler 운영 로그가 비어 있어(`Get-WinEvent` → unavailable) 추적 불가.
> **트리거를 모르는 채로 원인 수정을 시도하지 마라.** 이 항목은 원인 수정이 아니라
> **관측 추가**다.

경보는 **하나도 울리지 않았다.** 코디네이터가 파일 목록을 세지 않았으면 그냥 지나갔다.
`Get-ScheduledTaskInfo` 가 `LastTaskResult`/`LastRunTime` 을 그대로 내주는데
**워치독이 자기 형제 작업들의 결과를 안 본다.**

관련 작업: `tossmon-dailyhealth` · `tossmon-watchdog` · `tossmon-logrotate` ·
`tossmon-sentinel` · `tossmon-collector-oneshot`.

> 참고: `tossmon-watchdog` 은 `result=1` 로 남는데 **정상 동작 중**이다
> (`problems=...` 가 있을 때의 종료코드로 보인다). **확인하고, 정상이면 오탐하지 않게 하라.**
> 이걸 안 가리면 이 기능 자체가 (1)번과 같은 상시 경보가 된다.

### (4) `--date` 가 기존 리포트를 말없이 덮어쓴다

`ops/daily_health.py:326-327`:

```python
out = cfg.log_dir / f"daily_health_{label}.txt"
out.write_text(text, encoding="utf-8")     # <- 무조건 덮어쓰기
```

따라잡기 경로는 `write_if_absent` 로 **덮지 않게** 만들어 놨는데(`bf81c3b`),
사람이 `--date` 로 과거 날을 재구성하면 **원본이 사라진다.** 리포트 무결성이
§4.11 의 핵심이었던 만큼 이 구멍은 닫아야 한다.

## 할 일 (순서대로, 한 번에 하나씩)

각 항목마다 **고치기 전에 실패를 재현하는 테스트를 먼저 써라.**
기존 테스트 파일이 있다: `tests/test_ops_gap_audit.py`,
`tests/test_ops_daily_health_catchup.py`, `tests/test_ops_healthcheck.py`.

1. **(4) 부터** — 제일 작고, 나머지 작업 중 실수로 리포트를 날리는 것을 막는다.
   `--date` 도 기존 파일을 덮지 않게 하되, **사람이 명시적으로 덮으려는 경로는 남겨라**
   (예: `--force`). 덮은 경우/거부한 경우 둘 다 stdout 에 분명히 찍어라.

2. **(1) 로그 패턴 창** — 최소한 이 둘:
   - 경보 본문에 **매치된 가장 최근 줄의 타임스탬프**를 넣어라. 이것만으로도
     사람이 파일을 열자마자 "25시간 전 사건"임을 안다.
   - 창에 **시간 상한**을 걸어라. 값은 네가 정하되 **위 실측표(74~113분 vs 1,507분)를
     근거로 대라.** 상한 밖 사건은 경보를 내리지 말고, 내리지 않았다는 사실이
     보이게 하라(조용히 사라지면 그건 또 다른 사각이다).
   - 패턴 6개는 성격이 다르다(`CRIT` 인 `log_auth_failure` 와 `INFO` 인 `log_rankings_clamp`).
     **전부 같은 상한이 맞는지 판단하고 근거를 적어라.**

3. **(2) 결손 감사의 주말 창** —
   - 먼저 **월요일 창도 같은 증상인지 재봐라**(위 "미확인").
   - "장이 안 열린 창"을 `ALERT_` 로 찍지 않게 하라. **등급 체계는 이미 있다**
     (`ALERT_`/`TRADEOFF_`/`PLANNED_`/`NOTE_`, 08-05 사용자 결정 `b34a60a`).
     **새 등급을 만들지 말고** 기존 넷 중에서 고르고 **왜 그것인지 한 줄로 적어라.**
   - **"장이 안 열렸다"의 근거를 무엇에서 가져올지 네가 정하고 기록하라.**
     후보: 수집기가 이미 로그에 찍는 `telemetry session=closed`, 또는
     `tossmon/analysis/session.py` 의 세션 표.
   - ⚠️ **`session.py` 를 수정하지 마라.** 읽는 것은 허용한다. 다만 읽기로 했다면
     **애프터 종료 경계 08:50 → 09:00 변경이 대기 중**(사용자 결정, `COORDINATOR-STATE` §4.11)
     이라 그때 이 리포트 숫자도 함께 움직인다는 것을 문서에 명시하라.
   - **진짜 공백은 계속 잡혀야 한다.** 08-06 의 295.5분 `trailing_hole` 을 회귀
     테스트로 넣어라 — 주말 예외가 그것까지 삼키면 이 작업은 실패다.

4. **(3) 예약 작업 결과 감시** — 워치독이 형제 작업들의 `LastTaskResult` 를 읽고,
   비정상이면 등급을 매겨 경보하라. `tossmon-watchdog` 의 `result=1` 이 정상인지
   **먼저 확인**하고, 정상이면 그 값으로 상시 경보가 나지 않게 하라.

## 하지 말 것

- **수집기를 재시작하지 마라.** 이 변경들은 전부 재시작이 필요 없다
  (watchdog.ps1 은 5분마다 새로 실행, gap_audit/daily_health 는 예약 실행).
- **라이브 API 호출 금지.** 장은 월 22:30 KST 까지 닫혀 있고 리스도 없다.
- **`tossmon/analysis/session.py` 수정 금지** (위 3번 참조).
- **`0xC000013A` 의 원인 수정 시도 금지** — 트리거 증거가 없다. 관측만 추가한다.
- 쌓여 있는 `ALERT_*_log_precision_drift` 25개를 **손으로 지우지 마라.**
  고친 코드가 스스로 조용해지는지가 검증이다.
