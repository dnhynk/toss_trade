## 1. ★ 갈린 것 — **수집기 코드는 멀쩡하다. 기동 경로가 문제다**

같은 워크트리·같은 config·같은 venv 로:

| 경로 | 결과 |
|---|---|
| `python -m tossmon.collector --config config/config.yaml` (직접) | **18 초 만에 정상.** `resumed` -> `collector start` -> `session closed->pre` -> 텔레메트리 -> 테이프 폴 |
| `ops/launch_collector.cmd` -> `python -m ops.supervisor` -> 수집기 | **프로세스는 살아 있는데 stdout 0 바이트, DB 쓰기 0.** 재현됨 (21:28, 22:08 두 번) |

**즉 `ops.supervisor` 가 자식을 띄우는 방식에 문제가 있다.**

## 2. 가설 — **반증할 관측을 먼저 정해라**

가장 유력: **자식 stdout/stderr 파이프가 안 빠져 자식이 write 에서 블록된다.**

정황:
- `collector.stdout.log` 가 **204 MB** 이고 계속 자란다
- `detector.py:787` 의 `RuntimeWarning` 이 **초당 여러 줄** 쏟아진다 (앞단 실행에서 눈으로 확인)
- Windows 파이프 버퍼는 기본 약 64 KB — 안 빼내면 자식이 즉시 막힌다
- 증상이 정확히 그 모양이다: **프로세스 생존 + 출력 0 + 진행 0**

**하지만 확정하지 마라.** `ops/supervisor.py` 가 자식을 어떻게 부르는지
(`stdout=PIPE` 인가 파일 핸들인가, 드레인 스레드가 있나)를 **먼저 읽고**,
가설을 반증할 관측을 진술한 뒤에 고쳐라.

**다른 후보도 열어 둬라**: 콘솔/핸들 상속, `creationflags`, cp949 인코딩 예외,
로그 핸들러 충돌, 파일 잠금.

## 2-1. ★ 파이프 가설은 **죽었다** (코디네이터, 2026-08-20 01:1x — 코드 정독)

**§2 가 "가장 유력" 이라고 적은 파이프 교착은 성립하지 않는다.** `ops/supervisor.py:79-88`:

```python
log_fh = open(self.log_path, "ab", buffering=0)
return subprocess.Popen(
    self.cfg.collector_cmd,
    stdout=log_fh or subprocess.DEVNULL,
    stderr=subprocess.STDOUT if log_fh else subprocess.DEVNULL,
)
```

**자식 출력이 파이프가 아니라 파일 핸들로 간다.** 채울 파이프가 없으므로 자식이
write 에서 막힐 수 없다. **§2 를 쫓지 마라.**

### 대신 정독에서 나온 것 둘 — **둘 다 아직 가설이다**

1. **`log_fh` 를 열고 안 닫는다.** `_spawn` 이 매 기동마다 새로 열고 어디서도 닫지 않는다.
   재기동이 쌓이면 핸들이 샌다. **그 자체로 먹통을 설명하지는 못한다** — 다만 대상 파일이
   **204.5 MB** 이고, `"ab"` + `buffering=0` 으로 연다
2. **환경·cwd 는 용의자가 아니다.** `launch_collector.cmd` 가 `TOSS_BASE_URL`·`TOSS_LIVE=1`
   을 set 하고 `cd /d "%~dp0.."` 하며, 코디네이터의 앞단 실행도 같은 값으로 했는데
   **그쪽은 18 초 만에 정상**이었다. `collector_cmd` 도 절대경로 venv 로 올바르다(실측)

### 관측 하나 더 — 먹통일 때 **stdout 에도 한 줄이 없었다**

`collector.stdout.log` 의 마지막 쓰기가 **2026-08-19 21:19** 이고, 22:08 재기동으로 뜬
프로세스 넷은 **그 파일에도 아무것도 안 썼다.** 즉 자식이 **로깅 설정 전에** 멈춘다.

> **그러니 가르는 관측은 하나다: 휴장 창에서 `launch_collector.cmd` 로 실제로 띄워
> 어디까지 가는지 보는 것.** 코디네이터는 라이브라 그것을 못 했다. 그게 네 게이트 3 이다.

## 3. 함께 볼 것 둘 (같은 사고의 다른 얼굴)

1. **워치독이 자기 restart 에서 10 분을 멈춘다.** `ExecutionTimeLimit=PT10M` +
   `MultipleInstances=IgnoreNew` 조합이라 **한 번 막히면 그 뒤 트리거가 전부 무시된다.**
   워치독이 launcher 를 **동기로 기다리는지** 확인하고, 기다린다면 분리해라.
   **자가 복구가 이것 때문에 통째로 멈췄다.**
2. **`RuntimeWarning` 홍수.** `detector.py:787` 이 `calendar=` 미전달로 매 호출 경고를 낸다.
   파이프를 채우는 연료다. **경고를 끄지 말고 원인(캘린더 전달)을 고쳐라** — 끄면 다음에
   같은 함정을 못 본다. 소유가 W3/W4 면 **고치지 말고 보고**해라.

## 5-1. ★ 게이트 3 을 고쳐 적는다 — **라이브로는 못 한다**

옛 게이트 3(*"고친 뒤 `launch_collector.cmd` 경로로 기동해 로그가 붙는 것을 보여라"*)은
§2-2 (다) 때문에 **라이브 모드로는 수행 불가능하다.** 대신 이렇게 한다:

1. **비라이브 재현이 먼저다.** `launch_collector.cmd` 경로를 **`TOSS_LIVE=0` + 임시
   scratch DB + 임시 `state_path`** 로 띄워라 (라이브 워크트리의 `data/` 를 쓰지 마라).
   - **재현되면** — 그 자리에서 마음껏 붙잡고 고칠 수 있다. 그게 최선이다
   - **재현 안 되면** — 그 사실 자체가 정보다. *"라이브 모드에서만 난다"* 를
     적고 **거기서 멈춰라.** 라이브로 재현하려 들지 마라
2. 고친 뒤 **같은 비라이브 구성**에서 자식이 **초 단위 안에** 로그를 쓰는 것을 보여라.
3. **라이브 전환(사용자 콘솔 → 스케줄러 경로)은 네가 하지 마라.** 코디네이터가
   사용자 큐(**D-29**)에 올렸다. 절차와 되돌리기가 거기 적힌다.

### 왜 라이브 전환을 워커에게 안 맡기나

08-19 밤에 **코디네이터가 정확히 그것을 하다 17 분 동안 자가 복구를 스스로 막았다**
(`daily/2026-08-19.md` §9-2). 그리고 실패했을 때 되살릴 수 있는 유일한 확실한 손이
**사용자 콘솔**이다 — 에이전트가 앞단으로 띄운 프로세스는 Orca PTY job object 가
턴이 끝날 때 트리째 죽인다(`COORDINATOR-STATE` §5-3). **되돌릴 손이 없는 조작은
무인으로 하지 않는다.**
