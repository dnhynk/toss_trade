# W2 후속 — events 테이블 중복 방지 (라이브에서 발견된 버그)

너는 W2(`tossmon/store/**`, `tests/test_store*.py` 소유자)다. 짧은 후속 1건. **mock 전용**
(라이브 리스는 W5 보유 — 실서버 호출 금지).

## 문제 (라이브 수집 중 코디네이터가 직접 관측)
`events` 테이블에 **같은 (symbol, t0_ms) 이벤트가 여러 행으로 중복 기록된다.**
실측: 7분 수집에 15행이 쌓였는데 고유 (symbol, t0_ms)는 9개 — **40% 부풀려짐.**
```
DFNS 1785378480000 → 3행
GCTK 1785378840000 → 2행
LBGJ 1785403740000 → 2행
STKH 1785376860000 → 2행
SXTC 1785398880000 → 2행
```
원인: 검출기가 매 사이클 버퍼를 다시 스캔하며 같은 이벤트를 재검출하는데,
`events` 스키마에 `id AUTOINCREMENT` 만 있고 **(symbol, t0_ms) 유니크 제약이 없다.**

**왜 심각한가**: 이벤트가 중복되면 `evaluate.py` 의 q1~q6 통계가 전부 부풀려진다.
정밀도/재현율·기대수익 분포가 조용히 틀린 채 나오고, 아무도 눈치채지 못한다.
이 프로젝트에서 가장 비싼 실패 유형이다(계약 A1 §6 과 같은 부류).

## 작업 (소유 경로만)
1. `git rebase main` (main 은 0dc79d0 이상).
2. `schema.sql`: `events` 에 **`UNIQUE (symbol, t0_ms)`** 추가.
3. `writer.py` 의 `record_event`: **INSERT OR IGNORE 가 아니라 UPSERT** 로 하라.
   이유: 같은 이벤트라도 **나중 재검출이 더 나은 라벨을 갖는다** — T0 시점에는 peak_ms·
   peak_ret·ret_close 가 아직 확정되지 않았고 장이 진행되며 채워진다. 따라서
   `ON CONFLICT(symbol, t0_ms) DO UPDATE SET ...` 로 **최신 라벨로 갱신**해야 한다.
   단순 IGNORE 면 T0 직후의 미완성 라벨이 영구히 남는다.
   갱신 대상: kind, peak_ms, peak_ret, ret_30m, ret_close, session, meta_json 전부.
4. **마이그레이션**: 이미 라이브 DB에 중복 행이 쌓여 있다(오늘 밤 수집 중).
   스키마 버전을 올리고, 마이그레이션에서 **(symbol,t0_ms) 별 최신 행만 남기고 중복 제거**한 뒤
   유니크 제약을 거는 경로를 구현하라. `id` 가 큰 행이 최신이다.
   기존 DB 를 지우면 오늘 밤 라이브 데이터가 날아가므로 **반드시 보존 마이그레이션**이어야 한다.
5. **테스트**:
   - 같은 (symbol,t0_ms)를 라벨을 바꿔가며 2회 기록 → 행 1개, 라벨은 나중 값
   - 다른 t0_ms 는 별도 행
   - **중복이 들어있는 구버전 DB → 마이그레이션 → 행 수 축소 + 최신 라벨 보존** 검증
     (이 테스트가 핵심이다. 실제 라이브 DB 를 살려야 한다)
6. 전체 `pytest` 통과 확인.

## 주의
- **오늘 밤 라이브 수집이 돌고 있다.** 네 변경은 머지만 하고, 실제 DB 마이그레이션 적용은
  코디네이터가 세션 종료 후 지시한다. 마이그레이션이 **기존 데이터를 보존**하는지가 관건이다.
- 중복 자체는 사후 복구 가능하다((symbol,t0_ms)별 최신 행 선택). 그래서 세션을 중단하지 않는다.
