# W4 — 티어2 호가 수집 활성화 (W5 에스컬레이션, 이번 주 데이터 가치 직결)

너는 W4(`tossmon/collector/**`, `tossmon/config.py` 소유자)다. W5 가 막혀서 넘겼다:
**호가가 tier3 에서만 수집된다.** `loops.py:1497 run_tier3_micro` 가
`ctx.tiers.members(3)` 만 순회하고 `_poll_orderbook` 은 다른 곳에서 호출되지 않으며,
`config.polling` 에 tier2 호가 키가 없다(`tier3_orderbook_s` 뿐). ops 소유가 아니라
네 코드다.

## 왜 급한가

호가 수집이 tier3 승격 **이후**에만 시작되므로(중앙값 T0 +0.2분), **승격 전후 스프레드
궤적을 원리상 측정할 수 없다.** 이번 주 전략 설계의 핵심 질문 두 개가 여기 걸려 있다:
- 유동성이 몰릴 때 스프레드가 좁아지는가 벌어지는가 → **진입창 설계**
- 주문 크기에 따라 비용이 어떻게 늘어나는가(감사 A3) → **사이징·손익분기**

지금 실측: 최근 24시간 호가 321행 / 5종목(= tier3 뿐), 랭킹은 12만 행/578종목.
**수집이 안 된 시간은 영구 손실**이므로 오늘 장중에 반영되는 것이 최선이다.

## 작업

1. **tier2 저빈도 호가 라운드로빈** 추가 — tier2 멤버를 순회하며 심볼당 긴 주기로 1회.
   W5 제안은 심볼당 5~10분이지만 **숫자는 네가 실제 예산으로 정하라**(MARKET_DATA 그룹
   여유 안에서, tier3 고빈도 수집과 랭킹·캔들을 절대 밀어내지 않게).
2. `config.polling` 에 주기 키 추가(예: `tier2_orderbook_s`), 기본값은 보수적으로.
   **0 또는 미설정이면 비활성**이 되게 해서 되돌리기 쉽게.
3. 예산 방어: BudgetGuard 하에서 tier2 호가가 **가장 먼저 희생되는 우선순위**로.
   429 나 예산 압박 시 tier2 호가부터 건너뛰고 그 사실을 카운터로 노출
   (W5 워치독이 읽을 수 있게 이름을 보고에 명시).
4. 회귀 테스트: tier2 멤버가 주기에 맞춰 폴링되는지, tier3 주기가 영향받지 않는지,
   예산 압박 시 tier2 만 스킵되는지, 비활성 설정이 동작하는지.
5. 전체 pytest green. `w4-collector` 커밋.

## 반영 절차 (중요)

수집기는 **가동 중**이다. 머지 후 재기동이 필요한데, W5 가 검증한 안전 절차가 있다:
STOP 파일 생성 → 워치독이 자동 감지·재기동(공백 ~61초). **네가 프로세스를 직접 띄우지
마라** — 에이전트 자식 프로세스는 죽는다. 머지·재기동은 코디네이터가 한다.

## 불변 규칙

라이브 호출 금지(mock 전용), 가동 중 DB 접근 금지, 소유 경로 밖 수정 금지,
`main` 직접 커밋 금지, `worker_done` 1회(ASCII), (a)~(e) — (e)에 **선택한 주기와 그
근거(예산 계산)**, **워치독이 감시할 카운터 이름**을 적어라.
