= W5 — 워치독 디스크 회수 규칙 보강 (에이전트 스크래치 DB 사본)

너는 W5(ops 소유자)다. 오늘 실제로 터진 사고를 막는 작은 보강이다.

## 무슨 일이 있었나

여유 디스크가 10.9GB → **5.06GB** 로 급감했고, 네 워치독이 경보를 세 번 냈는데
(`disk_warn` 6.79GB → `disk_reclaim` 6GB 미만) **회수량이 0MB** 였다.

원인: **W3 가 분석할 때마다 수집 DB(약 500MB)를 통째로 스크래치패드에 복사**했고
지우지 않았다 — `live_snapshot.db`, `live2.db` … `live8.db` 로 **8개 3.9GB**.
락 경합을 피하려면 복사가 맞지만(코디네이터가 그렇게 지시했다), **매번 새 파일을 만들고
누적**된 것이 문제다. 네 회수 규칙이 **"24시간 이상 손대지 않은 파일"** 만 지우는데
이 사본들은 전부 당일 생성이라 하나도 안 걸렸다.

코디네이터가 수동으로 3.4GB 를 회수해 현재 **8.34GB** 다(최신 1개만 남김).

## 작업

1. **회수 규칙에 "에이전트 스크래치 DB 사본" 범주를 추가**하라.
   - 대상: `%LOCALAPPDATA%\Temp\claude\**\scratchpad\*.db` 류의 **대용량 사본**
   - 규칙 예: 같은 스크래치패드 안에 사본이 **2개 이상**이면 **가장 최근 1개만 남기고**
     나머지는 나이와 무관하게 회수. 크기 하한(예: 100MB 이상)으로 소소한 파일은 제외.
   - **활성 사용 중인 파일은 건드리지 마라** — 열려 있는지 확인하거나, 최신 1개는 항상 보존.
2. 회수 로그에 **무엇을 몇 MB 지웠는지** 남겨라(오늘처럼 "0MB 회수" 로 끝나면 원인을
   모른 채 경보만 반복된다).
3. **경보 문구 개선**: 회수 결과가 0MB 면 **최대 소비처 상위 5개를 경보 파일에 적어라.**
   오늘 사고에서 사람이 수동 조사해야 했던 이유가 그것이다.
4. 검증: 더미 사본 여러 개를 만들어 실제로 회수되는지, 최신 1개가 보존되는지,
   활성 파일이 안 지워지는지 확인하라(라이브 수집 무영향).

## 참고

W3 에게는 별도로 **사본을 재사용하도록**(매번 새 번호를 만들지 말 것) 지시한다.
이 워치독 보강은 그 규율이 지켜지지 않아도 디스크가 안 터지게 하는 **이중 방어**다.

## 규율

가동 중 수집기 접촉 금지(STOP 파일 경로만), 소유 경로 밖 수정 금지, `w5-ops` 커밋,
`worker_done` 1회(ASCII), (a)~(e).
